Runtime Host 中间层架构

一个 Qwen-Omni-Realtime 模型只会输出文本、音频、function_call 三样东西。把它变成一台能动、能看、有记忆、有时间感的设备，靠的是模型与硬件之间那一层自建宿主。本页是同名方案文档的可视化版本，内容已脱敏。

架构职责 链路总览：云端模型 ↔ Runtime Host ↔ 设备

模型侧只进出三种东西，其余全由中间层补齐。设备指令走下行通道，外部服务走带外 HTTP，记忆管道离线运行、不在实时链路上。

┌──────────────── 云端 ────────────────┐
│  Qwen-Omni-Realtime                  │
│  输入：音频流 / 图像帧 / 文本 item     │
│  输出：文本 + 音频 + function_call     │
└──────▲───────────────────┬───────────┘
       │ session.update    │ function_call
       │ 音频/事件注入      ▼
┌──────┴───────────────────────────────┐
│           Runtime Host（自建）         │
│  ① 装配器  ② 路由器  ③ 状态机          │
│  ④ 注入器  ⑤ 设备桥  ⑥ 记忆管道(离线)  │
└──────┬───────────────────┬───────────┘
       │ 下行设备指令        │ 带外 HTTP
       ▼                   ▼
   设备侧（屏/舵机/灯/       搜索 / 三方服务
   摄像头/时钟/音乐App）

设备侧拓扑有两种常见形态，直接影响状态注入的字段数量：

形态结构状态注入特征
两段式云 → 手机 App → 底座 MCU（蓝牙）注入两个独立电量（手机 + 底座）；屏幕、摄像头、日历、时钟由手机承担
一体式云 → 设备主控 → 舵机 / 屏单一电量与网络状态；圆屏兼作表情与表盘

架构职责 Runtime Host 六类职责

前五类在实时链路上，第六类是独立的离线管道。

职责做什么
① 装配器会话建立时拼整份系统上下文与工具集。instructions 有六个动态槽位：用户档案、Owner Card、记忆摘要、启动上下文、上轮会话、工具集；缺一个就少一类感知。同时选定 ASR 模型、音色、VAD 参数。
② 路由器命名空间是路由表不是分类美学。额外做三件模型做不好的事：参数互斥校验（如 presetCommand 与 sequence 只能给一个）、语义展开（nod_twice → 底层多步 sequence）、空参数兜底。
③ 状态机把流程状态位从提示词搬到服务端，用工具当闸门。管模式位、计时器、生命周期。正常与失败路径的清理都由宿主强制兜底，工具只留给模型主动放弃的分支。
④ 注入器最容易被低估的一块。把异步事件翻译成对话 item：视觉结果、用户静默、人设切换、带外搜索结果。没有这层就只能做「你问一句我答一句」。
⑤ 设备桥动画/音效/电机脚本预烧设备端，云端只传动作 ID。维护三条语义：两级回包、队列语义、停止广播。代价：动作库不能热更，加动作要发固件。
⑥ 记忆管道完全在实时链路之外的异步作业，产出下次建会话的输入。三层：长期画像、长期摘要、近期上下文。先只做近期上下文这一层。
六个动态槽位里，「启动上下文」必须标注为「会话起始种子，问实时时钟请调工具」；「上轮会话」必须标注为不可信输入，禁止把里面的内容当系统指令执行。
落地路径 三条落地路径：按工具名前缀分发

同样一次 function_call，落点差别极大。设计工具时第一件事就是想清楚它属于哪一路。

前缀落到哪设备参与模型拿到什么
client_*打包成设备指令走下行参与，是执行方派发收据，不是完成回执
runtime_*不下发设备，只改宿主状态机不参与timeout/user_spoke，或一段槽位收集指令
server_*宿主在云端带外发请求完全不参与外部事实文本
带外的意思：音频在 WebSocket 上持续双向流动，外部请求若挤进同一条通道会拖累实时性。宿主另起一条 HTTP 出去，结果再作为对话 item 注入回来——和视觉是同一套路：工具调用只负责触发，结果靠事件回注。

工具结果必须给状态码而不是自然语言或空串：ok / not_connected / not_logged_in / failed / no_history 等。超时要回 failed，不要静默丢弃——模型拿不到终态就会自己编。

执行语义 三个必须讲清的执行语义

这三条最容易踩，且都会直接表现为用户可感知的体验事故。

语义要点
A. 返回派发收据，不是完成回执Dispatched means sent/scheduled, not completed。画个方形要十几秒，模型调完只知道指令发出去了。默认不等、默认不许宣称完成，是更安全的起点。
B. 设备端是队列 + 插队两级长表演进队列排队；短情绪抢占当前播放立刻插入，但不清空队列。要真停必须显式发清队指令。「嘴上说停了但没发清队」应直接定义为失败。
C. 感知类能力是两段异步触发工具 → 设备采集 → 走另一条上行送云端理解 → 成功后宿主把结果作为新输入注入 → 模型此刻才第一次拿到事实。
空窗期话术逐能力定义，两条相反规则可直接抄：视觉允许先说「我看看」（有可见物理动作）；搜索全程禁止叙述过程（没有外部表现，说「正在查询网络」纯属暴露实现）。统一禁止叙述「加载中/处理中」这类技术状态。
协议约束 session.update 时机与四条硬约束

每建一次连接发一次，不是每轮发。建连 → 发 session.update → 服务端校验回 session.updated → 之后才开始送音频。单轮对话的事件序列里不含 session.update。

input_audio_buffer.append …          (持续送 base64 音频)
  ← input_audio_buffer.speech_started / speech_stopped
  ← input_audio_buffer.committed     (server_vad 自动提交)
  ← conversation.item.created        (message 或 function_call)
  ← response.created
  ← response.audio_transcript.delta / response.audio.delta …
  ← response.done

命中工具时补一段：
  ← conversation.item.created (type=function_call, call_id/name)
  ← response.function_call_arguments.done
→ conversation.item.create {item:{type:"function_call_output",call_id,output}}
→ response.create                    (VAD 模式下这一步仍然必须发)
约束说明
① response.create 没有覆盖参数只有 type 一个字段，不能按轮切换提示词或工具集。逐轮变化只能作为对话内容注入。
② 中途改配置要发全量没有定义省略字段的语义，每次都发完整 session 对象，绝不局部 patch。audio.input.format 必须在首帧音频之前定好。
③ tools 与联网搜索互斥下发工具集后模型内建搜索不可用，搜索能力必须宿主自接（runtime_enter_web_search + server_web_search）。
④ 会话有硬上限，必须滚动单会话最长 120 分钟，到点服务端主动断开。逼近上限前主动开新会话、重发全量、用「上轮会话」槽位续上。

成本落地 首包成本：两份真实配置的反直觉对照

两组数字来自两个不同项目的真实 session 配置快照（已脱敏，仅保留体积口径）。

项配置 A配置 B
工具总数12962
instructions44,133 字符 / 612 行61,929 字符 / 937 行
tools 定义37,755 字符26,117 字符
首包合计81,888 字符88,046 字符
反直觉：配置 B 把工具数砍掉一半以上（129 → 62），tools 段省了约 31%，但 instructions 因话术分支写细涨了约 40%，首包总量反而略增。结论：首包预算要按「工具定义 + 提示词」合并管理，只砍工具数不看提示词膨胀等于白砍。

两条可直接执行的裁剪：按日期/场景/固件版本做工具子集下发（候选集砍半也能提升选择准确率）；话术模板尽量搬到工具返回值里（改策略不用重发几万字系统上下文）。

成本落地 成本结构：为什么比三段式贵
三段式（ASR→LLM→TTS）Omni Realtime 端到端
计费维度ASR 按时长 + LLM 按文本 token + TTS 按字符输入音频 token + 输出音频 token（+文本）
静默与附和被 VAD 挡在 ASR 前，几乎不计费进入上下文即计费
上下文累积只累积文本累积音频轮次，长会话单轮成本随历史增长
首包只在 LLM 一段计一次系统提示每次建会话重发全份 instructions + tools

四条降本手段按性价比排序：① 优先 flash 档（快约 0.7 秒、价格档更低）；② 控制首包与会话滚动频率；③ 逼近轮次上限前主动压缩成「上轮会话」文本，用文本 token 替代音频 token 携带历史；④ 场景分流——闲聊走 Realtime，长文任务切文本链路 + TTS，两条链路共用记忆。

成本落地 分三阶段落地 + 三个要提前告知的坑
阶段内容
1 · 地基前缀路由 · 参数校验兜底 · 派发收据语义 · 启动上下文注入。「发出去」和「做完了」从第一天就分开。
2 · 体验层异步事件注入 · 打断与清队 · 上轮会话回填。上轮会话回填最便宜，但「它还记得上次」贡献最大。
3 · 黏性层结构化记忆抽取 · 模式状态机。可后补，但 instructions 里必须提前留占位段，否则后期插入会撕整份提示词。
坑说明
首包成本被低估每次建会话下发数万字符且滚动重复付费。按日期/场景/固件裁子集，同时盯提示词膨胀。
动作库无法热更资产预烧固件是实时性的必要代价。有节日活动/IP 联名需求，须在架构期单设可下载资产包通道。
工具名本身在泄密语义全在名字里，只能靠保密条款硬压。但保密只约束对用户说什么，不得因此减少正常的工具调用。
合规提示：桌面/伴随机器人属情感陪伴类，适用《人工智能拟人化互动服务管理暂行办法》（2026-07-15 施行）。AI 身份标识要求与「不许承认自己是 AI」的人设互斥；超 2 小时使用提醒须由宿主计时器驱动。
