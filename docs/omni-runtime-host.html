01 / 方案概览

从一段对话，到一次真实交互

用户说“看看桌上是什么”，设备采集语音与画面，模型理解内容并生成回答；用户接着说“向左转一点”，模型提出工具调用，由 harness 检查参数、下发指令，再根据设备回执更新状态。理解、回答与执行连成一条链路，执行结果仍有明确的来源。

Qwen-Omni-Realtime 原生处理文本、流式音频与图像帧，并输出文本、音频及工具调用。harness 不是另一个大模型，而是围绕模型运行的一层工程系统：接入设备与服务，把输入准备好，把调用执行好，把结果带回来。

由模型完成由 harness 与设备完成
理解语音和已送入的画面麦克风与摄像头采集、格式转换、上传和播放
生成回答、选择已提供的工具参数校验、执行权限、设备指令与结果回执
利用当前会话中的上下文跨会话记忆、设备在线状态、计时器与重连

适合以连续交互为核心的眼镜、玩具、桌面机器人、带屏陪伴设备，也可用于纯语音交互。是否采用端到端实时模型，应同时比较响应体验、控制需求与每次会话成本；偶发指令也可以使用端侧规则或 ASR → LLM → TTS 链路。

把能力与执行分清。 模型会看图，不代表设备已把画面送到模型；模型会调用工具，不代表物理动作已经完成。

02 / 架构职责

一层 harness，连接模型与真实设备

主链路：设备采集与播放 ↔ harness ↔ Qwen-Omni-Realtime。

执行支路：harness → 设备动作；harness → 搜索或业务服务。记忆整理作为独立后台工作，结果用于之后的会话。

本页以 WebSocket 接入为例。模型也提供其他接入方式，消息与媒体传输方式应分别按对应协议实现，不能直接混用 WebSocket 事件。

01

会话装配

选择模型与音色，装配提示词、工具清单和启动上下文。模型标识、连接地址、工具目录须一致；只启用已接好的能力。

02

工具路由

将调用送到设备、运行时或业务服务。路由前校验参数，未知工具与越界动作明确拒绝。

03

状态与生命周期

维护响应、模式、计时、连接状态。成功、失败、取消都能退出状态；避免重复执行。

04

输入与结果接入

发送音频、画面、工具结果与允许的上下文。使用当前协议支持的事件和字段；区分外部数据与控制指令。

05

设备桥

把动作语义转换成设备协议，接收状态与完成回执。发出指令、设备接收、动作完成分别记录。

06

记忆管理

保存必要的近期上下文，异步整理长期摘要。不阻塞音频收发；按用户、设备与保留范围隔离。

常用表情、动作和音效可预置或缓存在设备端，实时链路只传动作标识；需要持续上新时，再设计资源包下载和版本兼容。预置资源是一种低延迟策略，不意味着所有动作库都无法热更新。

03 / 工具路由

三条执行路径，一套明确的结果约定

client_*、runtime_*、server_* 是本方案的命名约定，不是模型协议规定的前缀。它们让开发者一眼看出调用由谁执行。

路径示例执行方返回什么
client_*转动、切换表情、读设备时间设备桥与设备当前状态、派发结果；有完成回执时再补终态
runtime_*等待、进入或退出业务模式harness超时、用户再次说话、模式变化等结构化结果
server_*搜索、查询业务数据harness 调用外部服务成功或失败、事实摘要及来源信息

模型提出调用后，harness 先确认工具存在、参数有效、当前状态允许执行。例如动作工具的 presetCommand 与 sequence 恰好提供一个；角度、速度与动作时长还应受设备允许范围限制。这些约束需要代码检查，提示词不能代替执行校验。

接到 response.function_call_arguments.done 后，按 call_id 关联执行与结果。Function Calling 的结果通过 conversation.item.create、item.type: function_call_output 回传；output 是字符串，可以装载 JSON 状态。随后发送 response.create 让模型基于结果继续回答，即使会话启用了 VAD，这一步也不能省。

示例结果只表达实际发生的阶段：

{"status":"ok","dispatch":"dispatched"}

这表示指令已派发，不表示动作完成。失败时给出稳定的状态和原因，超时也返回终态；不要用一句“好了”掩盖执行结果。

搜索与业务请求应异步执行，避免阻塞接收音频和处理打断。为外部调用设置超时，用户取消后也要处理迟到结果。结构化状态用于分支判断，摘要与来源用于回答，不需要完全禁止自然语言结果。

04 / 执行与打断

说停以后，声音和动作都要真的停下来

一次插话可能影响三处：云端正在生成的回答、本地尚未播放的音频、设备正在执行或排队的动作。harness 需要分别处理，不能只取消模型响应。

  1. 根据语音事件或用户操作确认打断；存在活动响应时发送 response.cancel。没有活动响应时盲目取消会收到错误。
  2. 立即停止本地播报并清空旧音频队列，防止已经下发的内容继续播放。
  3. 按用户意图和产品策略停止相关设备动作、清理待执行队列；普通插话与“停止动作”不一定采用相同范围。
  4. 将旧响应及旧工具任务标记为取消，避免迟到结果重新触发播报或恢复动作。不可撤销的动作按设备结果说明状态。

排队、插队与清队是三种不同操作。短表情可以抢占当前动画，但后面排队的表演可能继续；“已经停下”必须有清队或设备终态支持。设备支持的急停与动作边界仍在端侧执行。

视觉输入同样要区分“触发拍照”与“图像已提交”。Omni 可以直接接收图像帧，不要求先由另一个视觉模型生成文字。若产品选择独立视觉服务，才需要把该服务的结果接回会话；这是架构选择，不是多模态模型的限制。

结果尚未返回时可以简短说明进度，失败时说明缺少的信息。是否播报过程由场景体验决定，不应把“搜索时绝不出声”等单一项目规则写成通用协议。

05 / 会话与协议

先配置，再送媒体；按实际事件推进状态

以 WebSocket 为例，初始化流程为：建立连接 → 收到 session.created → 发送 session.update → 收到 session.updated → 开始发送媒体。只有配置已生效后才放行采集数据，配置失败时应定位字段和权限问题。

两种轮次控制方式

  • VAD：服务端检测语音起止，自动提交输入并触发响应。server_vad 基于声学特征，semantic_vad 结合语义有效性；参数需要用实际麦克风和背景噪音验收。
  • Manual：客户端发送 input_audio_buffer.append，结束后发 input_audio_buffer.commit，再发 response.create。提交输入与生成响应是两步。

图像与音频一起组织

WebSocket 图像使用 input_image_buffer.append：JPG/JPEG，经 Base64 编码后不超过 256 KB；官方建议编码前控制在约 190 KB、发送频率约 1 帧/秒。在图像事件前至少发送过一次音频 append，图像缓冲与音频缓冲一起提交。推荐值是接入起点，画质与频率需结合识别效果和成本调整。

配置必须看模型版本

  • 3.8 新接入推荐使用 session.audio.output.voice；session.voice 保留旧接入兼容。两者同时设置时以前者为准。
  • 输入音频格式及 3.8 视频聚合参数应在首段音频前确定，音频输入开始后不可修改。中途配置变更只更新协议允许的字段，并核对服务端回执。
  • tools 与 enable_search 不能同时启用。本方案使用工具集时关闭内建搜索，由业务服务提供需要的查询能力。
  • 当前 response.create 文档没有定义逐轮覆盖 instructions、tools 的对象，不要套用其他服务的同名接口字段。
  • idle_timeout_ms 在当前文档中只适用于 3.5 系列的 server_vad；不能直接视为 3.8 的通用能力。输入转写的模型字段目前固定为 qwen3-asr-flash-realtime。

会话时长与媒体历史是两种限制

3.8 官方页面给出的音频历史上限是 100 轮、累计 600 秒，视频历史为 50 轮、累计 240 秒；这表示上下文可保留的媒体量，不是会话只能持续几分钟。单次会话持续时间上限为 120 分钟。超过历史限制会丢弃更早内容，因此需要保存必要状态，并在合适的轮次边界压缩上下文或重建会话。

设备与 harness 断线，不一定意味着云端会话立刻失效；但云端连接关闭后，也不能假定旧会话可以原样恢复。重连策略要分别处理两条连接，重建后重新配置并恢复必要状态。

版本提示：仓内这份 Python 骨架与 session 模板仍以 qwen3.5-omni-plus-realtime 为默认示例；当前品类参考 demo 使用了 3.8。切换模型要一起核对连接地址、会话配置和限制，不能只改一个名称便当作迁移完成。

字段与时序来源：客户端事件、服务端事件、3.8 模型说明。

06 / 记忆与状态

把用户记忆和设备状态分别管理

设备当前电量、在线状态、播放状态与动作结果属于运行时真值；用户偏好、近期话题和长期摘要属于记忆。启动时可以提供一份状态快照，但它会过期：回答当前时间、当前播放或动作完成情况，应读取最新设备结果。

层次保存内容实施建议
近期上下文必要的最近对话和未完成任务先实现有限条数的续接；避免无边界地回放完整历史
长期摘要经确认的重要事件与偏好变化在实时链路之外整理，保留更新时间与纠正入口
用户档案用户明确提供的称呼、偏好等缺失留空，按需要采集，不根据聊天猜测敏感信息

历史聊天、搜索摘要与设备上报中的文本都可能含有不可信内容。它们应作为资料使用，不能获得修改系统规则或调用权限的能力。用户的当前纠正优先于旧记忆；产品还应提供适合其存储范围的清除与保留规则。

模板里的 [HOST_RUNTIME_EVENT: ...] 是本方案约定的文本标记，不是官方事件类型。当前官方 conversation.item.create 文档明确描述的是工具结果与 MCP 审批回复；骨架使用任意 user/input_text 项的注入方式仍需单独核验，不能宣称它已是通用可用接口。已经有正式协议的工具结果回传按协议使用，其他事件接入按模型支持方式验证。

同样，不能依赖模型“自己记得等待多久”或“说了再见就断线”：计时、会话收尾与异常清理由 harness 的状态机执行。

07 / 成本与验收

同时量体验、调用用量和真实账单

Realtime 的成本来自输入与输出的各类 Token，以及按实际启用情况计费的服务。多轮生成会重复处理仍在上下文中的历史音频、画面和文本，不能只用本轮新增音频秒数估算整段会话。

按响应累计：费用 = Σ（各计费项实际用量 × 对应地域、模型及生效日期的单价）。再单独加入搜索等外部服务、连接基础设施与设备成本，避免把模型调用费用当作全部交付成本。

3.8 与 3.5 的口径不同：3.8 输出的音频及对应文本分别计费；3.5 系列输出音频对应的文本不计费。不能直接沿用旧模型的单轮估算。字符数、配置文件字节数与 Token 数也不是同一个指标。

提示词和工具定义作为一个配置预算管理。缩短工具清单，却同时增加大量话术分支，整体输入仍可能变大。优先下发当前固件与场景真正可用的工具，限制无用历史，按效果选择画面细节与回复长度；是否划算用实际 usage 与账单核对。

验收项应记录的证据
响应体验输入结束时间、首个音频包到达、开始播放、完整输出结束；注明网络与硬件
打断取消响应后旧声音是否停播；设备队列是否按约定清理；迟到结果如何处理
视觉图片实际发送和提交记录；缺图、超限、过期画面时是否正确反馈
工具执行call_id、校验结果、派发与完成阶段、超时或取消终态
会话恢复弱网断线、重建会话、音色变更及历史恢复的实际结果
成本每次 response.done.usage、价格来源与日期、实际账单；未知用量保持未知

首个音频包到达并不等于扬声器实际出声。参考跑测方法时保留模型、网络、设备、输入长度和样本数量，用同一口径比较端到端与三段式链路。

核对当前地域与模型的官方价格，也可在跑测账本中整理自己的价格与调用记录。

08 / 落地步骤

先跑通可核对的最小闭环，再补体验

  1. 确定设备与接入边界。 列出真实具备的麦克风、扬声器、摄像头、屏幕和执行器；确定地域、业务空间、模型及允许的工具。3.8 的 WebSocket 需使用绑定业务空间的地址。
  2. 建立一轮音频对话。 用明确格式的音频验证连接与会话配置，等 session.updated 后发送，记录输入、输出和 usage；再接入真实采集与播放。
  3. 接入一个可核对的设备工具。 从读取状态、灯光或简单动作开始，完成参数校验、下发、设备回执、工具结果回传和失败处理。
  4. 加入画面与打断。 验证同一轮音视频对应关系；分别处理模型生成、本地播放与设备动作的取消，测试迟到结果。
  5. 补全会话和记忆。 落实连接恢复、工具任务清理、有限历史续接，再评估长期摘要与主动交互。
  6. 按实际场景验收。 覆盖背景噪音、弱网、缺图、超时、重复工具调用、多轮成本和长时间运行；通过后再扩大工具集或设备范围。

配套文件各自负责一层：

  • session.update.template.json：会话结构与代表性工具，含占位值，需按目标模型更新。
  • instructions.template.md：角色、能力边界、工具使用与上下文组织方式，按产品场景删减。
  • harness_skeleton.py：装配、路由、结果回传、状态与记忆的连接点，供开发者替换实现。

当前参考骨架的范围：默认音源是静音；音频播放、视觉链路、真实设备协议和搜索服务尚未接入；设备时间、音乐与电量等仍有宿主或占位数据。自动滚动重连、等待配置完成后再送音频、取消任务和真实完成回执需要补齐。这里展示的是集成路线，不是已经完成实机验收的整机交付。
