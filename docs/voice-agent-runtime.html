EXPLAINED / VOICE AGENT RUNTIME

从语音聊天到语音 Agent：
真正缺的是哪一层？

能听懂、能回答、能调用工具，还不等于能把一件事办完。真正困难的是：用户继续说话时，谁记得任务做到了哪里，谁有权让它继续，谁负责把结果及时送回来？

01 / TWO CLOCKS

先让它完成一份巡检草稿

设想一位工程师站在设备旁，对耳机说：“把刚才的巡检录音整理成清单，分清已经看到的异常和还要核对的地方，保存成草稿。”这不是开放式闲聊。完成标准至少包括一份文件、可回溯的观察，以及没有被擅自发送出去的边界。

十秒后，工程师补充：“先别念了，只保留需要复查的项目。”再过一会儿：“保存前让我确认。”后台可能已经在转写、检索或写文件。此时把最新一句话当成新的聊天轮次，只能得到一句听起来正确的答复；它并不能解释旧任务是否继续、哪一版清单会生效。

这里同时运行着两个时钟。对话时钟要求迅速回应、允许插话；工作时钟受到工具、网络、文件与审批限制，往往更慢。把两者塞进一个阻塞流程，用户会等得焦躁；让它们完全独立，系统又可能一边说“改好了”，一边交付旧文件。

语音 Agent 的核心进步，是让这两个时钟保持联系。不是每次都要上复杂后台：回答一句事实、调节本机音量可以很短；跨文件整理、检索与写入需要一个寿命超过单轮对话的任务。

02 / THE MISSING CONTRACT

中间这一层，负责让承诺和事实对得上

01 · CONVERSATION

对话前台

收音、判停、理解、回应、播放；把“我要改要求”表达成结构化请求。目标是保持交流连续。

任务意图 ↓   ↑ 状态与结果
02 · ORCHESTRATION

编排运行时

任务身份、要求版本、状态转换、授权范围、取消确认、结果归属与交付时机。目标是保持事实一致。

执行请求 ↓   ↑ 进度、产物、回执
03 · EXECUTION

后台执行

读文件、调用 CLI / MCP、检索、生成草稿；返回真实产物和失败信息。目标是完成有边界的工作。

这是职责划分，不要求每层都是一个进程，也不要求每层都再放一个大模型。一个 Gateway 可以承载前台接入和编排，后台则由另一个已配置的 Agent 执行。简单场景甚至可用明确的状态机完成大部分协调。

模型可以判断意图，不能仅凭模型说了“完成”就把状态写成完成。任务创建要有运行时记录，写文件要有工具结果，取消要有后台确认，播报要有客户端回执。若让这些事实都藏在聊天文本里，重试、断线和多任务并发时就没有可靠依据。

工程上可以把执行请求想成一个信封：task_id、revision、attempt、scope、context_ref。后台结果带着同一组关联信息返回。下文演练中的版本号是本仓的教学设计，并非声称两个上游都使用同名字段；它表达的是一个普遍约束：结果必须证明自己属于当前仍有效的工作。

03 / VOICE ONLY

qwen-audio-agent：让纯语音交互有工作记忆

在这个例子里，前台只接收语音，不需要视觉。qwen-audio-agent 通过可替换的实时语音 Provider 保持交流；需要持续处理的巡检任务由前台工具交给编排运行时，再通过后台适配器连接 ACP、A2A 等执行路径。语音前台与后台模型、工具、认证可以分别配置。

上游的任务机制把受理、执行、委派与完成分开。受理确认来自已经创建的 Task；后台可能进一步委派工作，但“委派成功”仍不是“任务完成”。适配器保留任务与后台会话的关联，最终结果再回到运行时。无关的会话更新不能把当前任务推进到成功。这正是“我听到了”和“我真的做好了”之间的区别。[1]

一个具体的接入方案

原型可以由电脑运行 Gateway，WebUI 或 TUI 提供麦克风与播放，语音前台使用可用的 Qwen Audio Realtime 服务，后台选择已安装并登录的 Qwen Code。测试目录只放非敏感巡检文本，任务范围限定为生成 inspection.md，不发送、不控制设备。先让前台聊天通，再接后台和权限提示，最后验收实际文件。

AGENT_PROTOCOL=none 可以用于前台连通性检查，但它不启动后台 Agent。若在这个模式下听到流畅回答，不能据此认定草稿已生成。没有执行能力时，正确体验是明确说明缺少后台，而不是用一段貌似完成的回答填上空白。[2]

演练：纯语音任务状态真实本地搭建步骤

网页用按钮代替说话，结果是人工样本；没有实际收音或后台连接。搭建步骤包含固定源码、Node 版本、健康接口和服务依赖，真实模型调用可能计费。

04 / CONTROL IS NOT CONVERSATION

四句话，需要四种不同的处理

同一巡检任务中的控制语义
用户表达运行时应处理的事实错误的简化
“先别念了”停播当前声音，保留后台任务直接杀掉任务，丢失工作
“只保留复查项”更新任务要求，旧结果不得覆盖新版只改聊天上下文，后台继续按旧要求做
“保存前问我”等待批准，绑定具体操作、对象与当前版本将模糊的“嗯”当成永久授权
“这件事不做了”发出取消请求，等执行侧确认前台答应后就显示已取消

停播只改变前台，取消改变后台

插话可能只是纠正一个名词，也可能是想让系统安静。把每次打断都映射成任务取消，会让长任务永远做不完；把所有打断都仅当作停播，又会忽略用户真正的终止意图。产品需要可区分的交互，也需要不同的控制通道。按钮、语音意图和状态提示应保持同一含义。

取消还存在“请求已发出”到“后台已确认”的间隙。qwen-audio-agent 的架构明确使用确认式取消，在此期间保持 cancelling；不能以模型的口头回应作为终态依据。即便取消成功，也只能阻止未发生的工作，不能自动撤销已经写出的文件或发出的消息。重试前应检查副作用、使用幂等标识或询问是否继续。[1]

修改要求，要处理正在路上的旧结果

假设 v1 包含全部观察，v2 只保留复查项。旧工具请求可能无法取消，也可能已经快完成。一个稳妥的做法是保留旧结果作为历史，但阻止它进入当前交付队列；必要时提取可复用的中间证据，再按 v2 重新整理。这样比“一律杀掉重来”省资源，但需要显式的版本关联与审计记录。

本仓演练用 revision + attempt 演示这个约束。修改要求增加 revision，失败重试增加 attempt；两者都能使旧结果失效。真实集成应使用上游提供的任务关联、适配器能力与更新接口，不要靠匹配一段结果文字来猜它是否过期。

批准是一个待解决的状态

授权提示应说明“写入哪个文件、做什么变化、属于哪个任务”，而不是只问“允许吗”。要求或目标变化后，旧批准不能偷偷延续。拒绝应返回一个可理解的结果，或者让用户缩小任务；不能把等待批准画成一直转圈的执行中。

同一事件，在三层里发生了什么？

切换事件查看机制。这是解释性示例，不会执行任务。

停播：后台仍在运行

前台停止当前音频；编排保留任务；后台继续处理。静音不是取消。

05 / DONE ≠ DELIVERED

工具做完了，用户为什么还觉得没做完？

后台生成文件只是第一道门。结果还要回到正确的会话，在合适的时候被呈现，并且避免重复播报。工程师可能正在与同事说话、设备可能断线，或者新手机刚接管旧会话。这些都是交付问题，不是再调一次大模型就能解决的问题。

qwen-audio-agent 将结果的上下文注入与播放确认分开：用户说话或已有响应时等待安全窗口，客户端的 playback.started 回执确认播放开始。已经开始播放的结果不因中途打断就反复重播；相关状态可持久化，重试有边界。播放开始仍不等于用户听完，更不等于用户同意草稿内容。[1]

因此，一份任务记录至少要区分“后台完成”“等待交付”“开始呈现”。需要用户确认的流程还应增加“已确认”。静音用户可以先看到任务卡，忙碌用户可以稍后听简短通知，详细产物留在可打开的位置。若只追求语音首包快，任务完成后却几分钟没有通知，体验仍然失败。

交付策略是一项取舍。尽早播报减少等待，却可能打断重要对话；等安静再说更自然，却需要可见队列与超时提示。紧急告警应有专门设计和验证，不应把普通 Agent 的通知队列当作安全系统。

测量时也应分开：从用户说完到任务受理、到真实产物生成、到播放开始、到人工确认。把这四个时刻压成一个“延迟”数字，会掩盖最影响用户的等待阶段。

06 / CONTEXT HAS A LIFETIME

Qwen-Live-Harness：让“这里”指向可核对的画面

同一巡检任务加上视觉后，用户可以说：“把这里看起来不对的地方放进清单。”现在系统还必须知道“这里”指哪一帧、来自哪个显示器或相机、是在用户说话前还是说话后采集。画面可能已经切换，模型看到的却仍是旧截图。

Qwen-Live-Harness 将 Electron Host 和 Node daemon 分开：Host 处理界面、系统权限、音视频采集与播放；daemon 连接 Omni Realtime、调度工具、后台 Harness、主动观察和记忆。两者通过本机 WebSocket 协作，使用配套版本。完整桌面体验当前要求 macOS 12+，源码开发要求 Node.js ≥22.13 和 Xcode 命令行工具。Linux 上通过纯脚本测试不能证明桌面链路可用。[3]

视觉的三种路径解决不同的问题
路径数据流与用途代价 / 盲区
On Demand所选来源截图 → 独立视觉子智能体 → 主对话；适合“看看这张图”上下文是一个快照，随后就可能过期
Live Feed持续图像 → 主模型；默认 1 FPS、720p增加传输与推理负担，抽样仍会漏掉短事件
Proactive Monitor独立观察条件，按 1 FPS、每轮 2 秒；通知排队返回有采样、推理和播报延迟，可能误判，不是安全报警系统

具体方案：先观察，再形成草稿

在 Mac 上打开两张非敏感巡检照片，显式选择显示器与 On Demand。先问铭牌能确认什么，再切到接口近景，要求“只依据新图，列待核对项”。若要生成文件，另接已配置的后台 Harness，并批准测试目录的写入。看图、写文件、发送文件是三个能力边界；视觉授权不会自然扩张成写入或发送权限。

本仓的视觉演练用预制情境 A / B 表达截图变化：切换后增加要求版本、撤销旧批准，并拒收旧结果。真实工程可以把画面哈希、来源、采集时间与任务关联，遇到敏感操作前再采一次并重新确认。这些是本文提出的集成设计，不应读成上游已经保证了任意屏幕操作的原子性。

持续视觉有助于省略反复描述，但也扩大了误采集与信息暴露的范围。按需模式更容易解释“这一刻看到了什么”，连续模式更适合动态语境；两者都需要清楚的采集指示、停止入口和上下文过期策略。记忆保存在本地也不代表记忆整理、向量化等推理不走云端。[3]

07 / TOOLS NEED A HOST

CLI 与多模态插件，是可执行工作的材料

Bailian CLI 可以把录音转成文本、合成一段播报、生成插图，或发出文字请求。Qwen-MM-Plugins 可以检查视频元数据、抽帧和裁图，也有调用专门模型服务的能力。这些工具让后台工作变得可执行，但它们不会自动替产品管理“用户刚刚改口”“现在还没批准”或“结果应送给谁”。

巡检任务里可以先用 CLI 转写录音，用 MM core 定位证据帧，再由后台形成草稿。core 原生工具把图像返回宿主，不另发模型请求；宿主推理仍可能收费并发送图像。CLI 接受本地媒体路径时可能上传临时服务存储。把工具运行在本机，不等于数据与模型都在本机。[4] [5]

工具选择也有实际取舍：一次直接调用短小、容易验收；让后台 Agent 自主规划适合多步任务，却引入更多失败点和权限需求。能用明确参数和验证器解决的步骤，未必值得再加入一个协调模型。反过来，把跨文件任务硬塞进单次调用，也会丢掉中间证据和恢复能力。

关于这四组能力的内容、架构、运行步骤和多个 Demo，已独立收录到能力实验室。这篇文章解释为什么要这样组合；实验室负责让开发者逐条尝试和验证。

08 / TEST THE PROMISE

验收的对象，应当是一次完整承诺

对硬件团队来说，最先值得做的原型不是漂亮的唤醒动画，而是一件有输入、有产物、有失败路径的工作。先在电脑完成巡检草稿，再考虑把麦克风和播放迁到耳机、眼镜或桌宠。迁移时仍需处理回声消除、网络断开、设备身份与真实动作回执。

  1. 受理有凭据。记录任务 ID 与当前要求；没有后台时明确拒绝办事。
  2. 交互不中断工作。插话与停播不误取消；修改要求后人工检查最终文件确实对应新版。
  3. 权限有对象。待批准时不继续敏感动作，拒绝能结束或缩小任务；旧批准不能用于新目标。
  4. 取消有确认。先显示请求中，再依据执行侧回执更新；模拟迟到结果，确认不会复活已取消任务。
  5. 失败可恢复。工具超时、空结果、后台退出都不冒充成功；重试前核对已有副作用。
  6. 完成后能找到结果。用户讲话时排队，恢复后交付一次；断线重连不会发给错误会话，播放开始与用户确认分别记录。
  7. 视觉有时效。切换来源、撤销采集权限后不会继续宣称看见当前画面；关键操作前重新取证。

如果这一组测试过不了，再流畅的语音也只是更自然的界面。过了之后，产品才有能力作出一个可信的承诺：任务正在做，变化已经记住，结果会在合适的时候回来。
