同一句话，三种厚度：
语音硬件后面到底差在哪

同一句人话，三种方案。你听到的后半段不一样，机器背后跑的也不一样。

本文内容
周五晚上那句话L1 · 听见并分发L2 · 把事办完L3 · 生成再落地对照一张表读案例三问L2 深挖附录改口旧画面晚一点播报开发者说明与来源

分层怎么划，写在仓库说明的 AI 硬件方案分层。这篇接着那一节，把同一句话听完。

周五晚上，同一句话

周五晚上七点半。你抱着娃从幼儿园回来，手里还拎着要修的标签机。沙发上的音箱亮了一下。

你随口说了一句：

客厅灯调暗一点。明天带她去看牙，帮我看看还缺啥；再给她打一张小奖状，说她今天很勇敢。

下面不是产品说明书，是三种常见方案同一句人话时，你会听到什么、机器背后实际跑了什么。

L1 · 只有「听见 + 分发」，没有复杂 harness

你听到的对话

  • 你：客厅灯调暗一点。明天带她去看牙，帮我看看还缺啥；再给她打一张小奖状，说她今天很勇敢。
  • 设备：好的，客厅灯已调到 30%。明天有「看牙」日程，在上午十点。要我设个八点半闹钟吗？
  • 你：闹钟就算了。奖状呢？
  • 设备：我可以给你念几句鼓励的话。要打印的话，请在手机 App 里选模板，或对接打印机后再试。
  • 你：……行吧，灯留着就行。

对话之后的执行链路

语音识别
  → 意图分发 / 中控
      ├─ device.control(light.living, brightness=30%)   ✅ 执行并回复
      ├─ qa.calendar("明天看牙")                         ✅ 读日程，口头答一句
      ├─ intent: 生成奖状 + 打印                         ❌ 无工具 / 无 harness
      └─ 可选：push「去 App 完成」                        （把事甩回给你）

没有多步规划，没有「先查缺什么再生成再送打」。贵的是听得懂、控得住；常见授权大约 1～10 元/台/年，市场上也有 <5 元/设备终身。智能音箱、简单物联、基础语音遥控，多半停在这一层。

L2 · 语音当界面，后面有 harness 把事办完

同一句。灯还是要调，但「看牙还缺啥」不再只是问答。

你听到的对话

  • 你：客厅灯调暗一点。明天带她去看牙，帮我看看还缺啥；再给她打一张小奖状，说她今天很勇敢。
  • 设备：灯调好了。我先按明天的看牙日程列个清单，列完念给你听，你说「行」我再写入备忘。奖状我这边还画不了，清单里我先留一项「准备小奖励」。
  • （大约二十秒，你在给娃脱外套）
  • 设备：清单好了：医保卡、病历本、之前的牙片——日历备注里写过「带上次片子」；水杯；到了别吃东西——预约短信里写了检查前两小时禁食。要我写进「家庭备忘」吗？
  • 你：写吧。奖状真没有？
  • 设备：这台方案没有生图和打印机通道。要奖状，得换带生成或外设的方案——或者你手机里做。

对话之后的执行链路

语音识别
  → 意图分发
      ├─ device.control(light…)                    ✅ 立刻做
      └─ 交给 Harness / Agent 运行时（本地或云）
            → 读日历「看牙」
            → 读预约短信 / 备注（工具）
            → 汇总缺口清单（多步）
            → 等你口头确认
            → notes.save(清单)                     ✅ 真正落盘
            → 奖状：无 image.gen / 无 printer      → 诚实降级

前台可以说「我先列清单」；后台才是 Qwen Live Harness、DeepSeek Harness、千问办公、WorkBuddy 这类在跑。相对 L1，贵在能办事，不在能听见。

插一句现有科普里强调过的坑：你如果中途改口「别写入了」，L2 必须能取消或改版本那次 notes.save，不能只把耳机里的话换掉——那是编排层的事，不是又回一句「好的」就够。改口怎么收、画面会不会过期、结果要不要马上念，放在文末 改口、旧画面和晚一点播报。

L3 · 还是语音入口，再叠生成，接到外设

奖状不再被挡在门外。

你听到的对话

  • 你：客厅灯调暗一点。明天带她去看牙，帮我看看还缺啥；再给她打一张小奖状，说她今天很勇敢。
  • 设备：灯好了。清单我按看牙日程在整；奖状我按「今天很勇敢」出一版儿童插画，你看一眼，点头我再送到儿童打印机。
  • （娃问：奖状有恐龙吗？）
  • 你：加只小恐龙。别保存清单，先让我看奖状。
  • 设备：清单先不动。恐龙版出来了——要不要我读一下上面的字？
  • 你：不用念。字改成「今天看病也不哭」。打印吧。
  • 设备：已送打。一份在打印机队列里。

对话之后的执行链路

语音识别
  → 意图分发
      ├─ device.control(light…)                 ✅
      └─ Harness（可与 L2 同栈，或更薄的「生成流水线」）
            → calendar + 备注 → 清单草稿（可被你叫停）
            → image.gen(勇敢 + 恐龙 + 文案迭代)   ✅
            → 等你接受（「打印吧」= 批准）
            → printer.job(儿童打印机)            ✅ 物理闭环
            → notes.save                         ⏸ 你说了先别写

儿童打印机「一句话生图并打印」，就是典型 L3。它可以叠在很薄的中控上（几乎只做生成+外设），也可以和 L2 的 harness 同在：先办事，再生成，再落地。

往后读案例时，先问三句

  1. 入口是不是语音（或极简界面）？
  2. 有没有 harness——能不能把多步任务做完，而不只是答一句？
  3. 有没有生成或物理输出闭环？

卡片上写「AI 在哪」，尽量落到 L1 / L2 / L3（可叠加），别只写「带 AI」。

附录 · L2 深挖：改口、旧画面、晚一点播报

上面那张表把厚度分开了。真要做成 L2，还有几件容易混在一起的事：人改口时，后台那步做没做完；「这里」是不是模型刚看到的那张图；结果写好了，要不要立刻念出来。这些仍算在 L2 里，价位也还是上面那一栏。

例子换回一台偶尔断连的标签打印机。仍然是假设，好把机制说具体。

一句补充之后

假设你刚检查完办公室里那台偶尔断连的标签打印机。电源灯一直亮着，接口处有没有接触不良，还没查清。你录下观察，拍了两张照片，回到电脑旁，把转写好的记录和照片放进同一个目录。这是本文设定的情境，接下来想让语音助手帮忙整理一份检查清单。

你说：「把记录整理一下，先别保存。」助手开始复述。听了两句，你觉得没必要从头听，便打断它：「不用念，只留下还没确认的地方。」

这句话很短，却同时改变了两件事。耳机里的声音应该停下来，清单的内容也得跟着改。正在整理记录的程序可能已经走到一半，它收到修改了吗？刚才生成的那份初稿还算数吗？

如果只是聊天，这些细节不太显眼。补充的话进入上下文，下一句回答就可以接上。但一旦助手开始读文件、调用工具、准备保存结果，对话之外便有了正在发生的事情。你说话的速度，往往比这些事情完成的速度快。

一种省事的做法是让用户等着：工具跑完，助手再听下一句话。这样容易安排程序，却很难让人愿意一直用。人在等待时会想到补充条件，也会发现刚才说错了。尤其戴着耳机、手里还做着别的事时，没人想为了修改一个要求，先听完一段过时的回答。

允许插话以后，麻烦才显出来。播放可以停下来，已经发出的请求却未必收得回来。前台答一句「好的」只花很短时间，后台可能仍在按旧要求整理文件。用户能听见的部分与机器实际在做的部分，由此出现了距离。

让对话继续，得有人记住那件没做完的事

qwen-audio-agent 值得拿来讨论，正因为它试着处理这段距离。用它搭一个纯语音原型，可以让电脑承载服务，麦克风和耳机负责交谈，再接一个已经配置好的后台 Agent，去读记录、整理内容和生成文件。实时语音模型留在对话里，不必等整个整理过程结束才回应用户。

这并不意味着只要听到「正在处理」，后台就已经开工。按项目的设计，前台确认受理之前，运行时要先创建任务记录。后台接到工作以后，结果也得沿着这项任务的关联返回。把工作交给另一个程序，只能说明委派发生了；那个程序最后有没有产出文件，还要继续等它的结果。[1]

这里便能看出编排运行时的用处。实时语音前台负责听懂刚才的补充，后台负责整理文件，中间的程序记着这份清单做到哪一步、现在按什么要求做、有没有在等批准。它把对话中的变化送到对应的工作上，再把执行的进展带回来。所谓「中间这一层」，做的是这些具体的协调。

这层协调未必还需要一个大模型。给任务一个身份，保存状态，核对回执，很多工作适合由普通程序完成。模型仍然要理解「只留没确认的」指什么；但它说出「已经改好」，不能代替程序确认后台确实收到了修改。

如果拿这个项目复现开头的情境，可以先只给它一份无敏感信息的文字记录，让后台在测试目录里生成 inspection.md。这里用纯语音下达要求，照片暂时不参与。一次把录音、视觉、设备控制都接上，出了问题反而难以知道是哪段链路没通。

整理所需的工具可以逐步加进去。例如，Bailian CLI 负责把录音转成文字，Qwen-MM-Plugins 帮忙读图片或抽取视频帧，后台再据此起草清单。每个工具多解决了一步，也多了一个可能等待或失败的地方。短任务用一次明确的调用就够了；需要反复查材料的工作，才更值得交给能够持续执行的后台。

可以先在纯语音任务演练里试着停播、改要求和取消。网页用按钮代替说话，展示的是本地状态变化，不会收音或连接真实模型。

改口以后，已经开始的工作怎么办

回到那份检查记录。最初的要求是整理全部观察，后来改成了只保留待确认项。假如初稿刚好在这时返回，它可能写得很完整，却已经不适合交给用户了。再让前台润色一下措辞，也解决不了内容范围过时的问题。

一种处理办法，是给每次修改留个版本标记。第一份初稿属于旧要求，可以暂存为历史，等按新要求整理的结果回来后，再交付新版。已经读出的记录、已经找到的证据未必需要丢掉，能复用就不必重查。这样节省时间和调用成本，代价是程序必须记清楚哪些材料还能用，哪些结论需要重做。

实际接入时，还得看后台支持怎样的修改。有的能在执行中接受新指令，有的只能结束当前步骤后继续，有的需要另开一次尝试。qwen-audio-agent 会把调整送向已关联的任务；能否在执行中改变工作，取决于后台的能力。聊天里补上一句要求，并不会自动让所有工具请求改变方向。[1]

保存文件又多了一层等待。开头说过「先别保存」，那么清单即使已经整理好，也应该停在预览处。此时询问「是否保存到 inspection.md」，用户才能判断接下来会发生什么。如果批准后又改了内容，也得核对这次批准是否仍适用于新版本。实现这样的流程，需要把批准和具体的文件操作关联起来，单靠模型记住一句提醒并不稳妥。

至于「不用念了」和「这件事不做了」，两种意思必须分开。前一句只需要停止播报，整理工作可以继续。后一句则要把取消请求送给后台，等它确认后，才能告诉用户已经取消。qwen-audio-agent 为这段间隙保留了取消中的状态，避免把口头应答当成执行结果。[1]

即便收到了取消确认，也不能假定此前什么都没发生。文件可能已经写出，外部消息可能已经发走；这些事得另外核对。重试同样如此。一次调用超时，只能说明这边没有及时收到结果，并不能证明对方没有做过。若不先检查就再试一次，用户的一句话可能留下两份文件，甚至触发两次操作。

它看见的，可能还是上一张照片

文字清单整理到一半，你想起目录里还有照片，于是在屏幕上打开它们。第一张拍的是打印机铭牌，第二张是接口近景。你切到第二张，说：「这里看不清，把这个也记到待确认项里。」

人坐在同一台电脑前，通常知道「这里」是哪儿。模型未必知道。它收到的截图也许还停在铭牌那张，语音却已经在说接口。这样的回答可能语句通顺，甚至把上一张图描述得很准确，但用在眼前这件事上就是错的。

Qwen-Live-Harness 提供了一个带视觉上下文的接入例子。在 Mac 上，由桌面 Host 处理麦克风、屏幕或摄像头的授权与采集，再交给后台 daemon 连接模型和工具。选择 On Demand 时，一次截图由独立的视觉子智能体分析，结论回到主对话；选择 Live Feed，则持续把画面送给主模型。[2]

对于这两张检查照片，按需截图已经很有用。打开接口图以后，明确请它看当前画面，再讨论哪些地方无法确认。持续送图可以少一次提醒，但不会消除时间差。项目默认的 Live Feed 是每秒一帧、720p，窗口切换或短暂出现的内容仍可能漏掉。采集越频繁，传输和推理的负担也越重，而且用户得更留意屏幕上还有什么会被带进去。

因此，做产品时值得把截图的来源和时间留下来。若用户已经换了照片，或者距离取样过去了较久，就重新取一张，再让后台继续。这会多一点等待，却能让人发现助手依据的是旧画面。本站的视觉演练还会让旧批准和旧结果随着画面变化失效，这是演示一种可采用的协调方式，不能据此推断上游已经保证所有屏幕操作都如此处理。

看见接口图之后，下一步依然只是补充清单。要把清单写成文件，仍需接入有执行能力的后台；要把它发送给别人，又是另一项需要授权的操作。屏幕访问权限只解决了输入从哪里来，并没有一并回答这些问题。

视觉上下文演练里可以切换两张示意图，观察画面过期后任务如何暂停。它使用本仓预制图片，不读取当前屏幕；实际 Mac 上的看屏步骤见文末开发指南。

清单写好了，还得等一个合适的时机

假设你已经核对预览并允许保存。后台写好了文件，偏偏这时旁边有人来问打印机的情况，你正戴着耳机和他讲话。助手如果立刻把清单念出来，就会打断交谈；如果一直安静，你又可能以为刚才的任务没有做完。

qwen-audio-agent 把结果回到对话与开始播放分开处理。用户正在讲话，或者已有一段响应在播放时，结果先等一个合适的窗口。音频实际开始播放后，客户端会回传确认；只有服务端生成了声音，还不足以说明耳机已经播出来。已经开始播报的结果，也不会因为中途被打断就一遍遍从头重念。[1]

这个回执仍然有边界。它表示播放开始，不能证明用户听完，更不能代替用户同意文件内容。对这份检查清单来说，留下一个随时能打开的文件入口，往往比要求人把整段播报听完更合适。短通知可以稍后说，详细内容可以之后看。

视觉助手也会遇到同样的选择。Qwen-Live-Harness 的主动观察会把通知排队，等当前对话和播放结束后再播报。这适合一般提醒，却不能拿来保证紧急告警一定及时到达。采样、推理和等待播放都需要时间，产品得按用途决定能等多久。[2]

到这里，那台打印机是否真的接触不良，仍然需要人检查。助手能完成的，是把已经看到的情况与尚未确认的地方分清，按修改后的要求保存，并把文件送回到用户手边。打开清单时，那一行应当写着「接口状态待核对」，而不是替一张模糊的照片下结论。

留给准备动手的读者

附录里的打印机检查是一个假设任务。版本关联、旧批准失效和画面过期策略是本文的集成建议，本站 Demo 用本地状态逻辑演示这些做法，不代表已经接通上游服务。网页和 Node runner 均无模型请求；真实本地路径见四组能力开发指南，其中另有 CLI 命令模板和媒体证据演练。

纯语音方案可从电脑上的 Gateway、WebUI 麦克风和已配置的 Qwen Code 后台开始。AGENT_PROTOCOL=none 只用于前台聊天，不执行后台任务。本文依据 main 提交 d2a8dc4；仓内 Demo C / D 使用已发布的 npm 2.0.1，默认模型和前台 Key 变量有所不同。安装时沿同一条版本路径操作；/api/health 返回正常，也不代表一次任务已经成功。

视觉方案的完整桌面路径需要 macOS 12+、Node.js ≥22.13；源码构建还需 Xcode 命令行工具，Host 与 daemon 要配套。项目的主动观察按每秒一帧、每轮两秒运行；记忆虽保存在本地，整理与向量化仍会调用配置的模型服务。具体设置和依赖以固定源码及开发指南为准。

CLI 接受本地媒体路径时可能上传临时服务存储。MM core 原生媒体工具不另发模型请求，但宿主理解图像仍可能走云端并计费。本文没有付费模型、真实语音、macOS Host 或整机实测；已做与未做的检查见验收记录。
