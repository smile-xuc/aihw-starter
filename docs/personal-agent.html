Personal Agent 设备，会是什么样？

个人助手正在从「能聊天」过渡到「能办事」：读邮件、改日程、整理纪要、在浏览器里跑腿、在支付环节下单。公开产品在这一阶段给出的差异，主要不在对话文案，而在三处工程选择——任务闭环跑在谁的机器上、外向动作由谁批准、真实凭证是否进入模型上下文。

1. 场景：个人 Agent 常办的四类事

下面四类场景在输入、中间状态、外向动作上结构相近；差别主要在闭环落在本机还是「一人一电脑」的云执行面，以及哪一步必须过审批。

1.1 邮件与日程

输入通常是邮箱与日历同步流，加上用户口头或文字意图（摘要、起草、改期、找空档）。中间状态包括线程上下文、联系人偏好、已有会议冲突、草稿版本。外向动作是发送邮件、创建或修改日历事件，有时还包括退订或批量归档。

同步本身几乎总会连到邮件服务商：Underdog 写明邮件在用户电脑与邮箱提供商之间直连，摘要与起草在本机模型完成；Muse、dots、Grok Bot 则通过连接器或插件访问邮箱，读与写往往分开授权；OpenMausBot 的公开说明把 Gmail 等接入写成经 Composio 的 OAuth 会话，连接后多个 Bot 可共用同一连接器面。Lightning Demo 里 Muse 连接 Gmail / Calendar 时，界面表述偏「邮件可读、日历事件可删」，与「读宽写窄」一致；发送侧对照也很整齐——Muse 把发信列为需确认的敏感动作；dots 用 auto-review 与 Custom Rules 决定免问、先问或交给用户；Grok Bot 对「用户未在当轮明确要求发出」的邮件、例程触发的外发，常先落成 draft，等人点 Send；Underdog 在本机侧对敏感下一步要求批准后再发出；OpenMausBot 文档把外发类敏感步放进 permission broker 的 Allow / Deny 卡（具体覆盖面随引擎与工具而变，仓库说明写明并非每一步都保证暂停）。读收件箱可以较宽，写出发信则普遍更窄：这是几类产品里重复出现的权限切分。

1.2 会议纪要

输入是录音、导入音视频或会后文本。中间状态是转写、摘要、决议与待办条目，以及这些条目与联系人、项目的关联。外向动作可能是把待办写进日程、把纪要发到邮件或协作工具。

原文与派生摘要「住在哪」直接绑定产品信任边界：Underdog 将录音、笔记、转写放在本机；Muse 把工作区与记忆放在用户自己的 Secure VM 内，并支持对已学内容说 forget；dots 使用 ChatGPT memory 与 dot 自建 notes；Grok Bot 按 Bot 保留偏好与工作摘要，同账户多个 Bot 共享一台云电脑上的文件与浏览器会话；OpenMausBot 把 transcripts、keys、events 默认落在本机 ~/.openmausbot，按 Bot / channel 分线程，工作文件夹可按任务另挂。纪要是否离机、是否进入训练轨迹，取决于各产品默认策略与用户开关（例如 Muse 的训练 opt-out、dots 个人计划上的训练控件；OpenMausBot 文档写明提示词会发往所选模型提供商，本地存储不等于模型请求不出本机），而不是「有没有纪要功能」本身。

1.3 浏览器跑腿

输入是比价、填表、订位、查政策、整理资料一类目标。中间状态是浏览会话、页面结构摘要、多步骤任务进度、失败重试记录。外向动作是提交表单、创建预订草稿、下载文件或进入结账页。

执行面分叉很清楚：Muse、dots、Grok Bot 默认在云端浏览器里操作，用户可随时接管。Lightning Demo 里订票时，聊天内嵌的是 Muse 自有虚拟机上的 persistent 浏览器视图，并提供「Take control of the browser」把验证码、密码或纠错交回人再交还 Agent；Underdog 使用本机浏览器与本机模型；Qwen-Live-Harness 的前台 Realtime 会话可以继续聊天，同时把改文件、跑命令一类工作委托给本机 ACP / CLI 后台 harness；OpenMausBot 则把每个 Bot 的「电脑」写成可选面——Boat 云 Linux 桌面、隔离 Local VM，或在平台安全边界已认证处显式 opt-in 后的本机控制（文档写明 macOS / Ubuntu Xorg 可开，Wayland 主机控制仍关闭），云桌面侧提供预览与「Open desktop」接管。渠道能对话不等于已授权浏览器或本机：dots 文档写明，消息渠道、插件、本机连接是三套独立授权——在 Slack 里能提到 dot，并不自动打开 Gmail 或用户笔记本；OpenMausBot 同样把聊天、连接器与电脑访问拆开启用。站点若拦截自动化、会话过期或需要人机验证，公开产品普遍选择把步骤交回用户，而不是绕过登录墙。

1.4 支付与下单

输入是购物或订票意图与约束（预算、商家、时间、退改规则）。中间状态是比选结果、商户页上下文、待确认金额。外向动作是生成支付凭据并完成扣款，或把购物车留给用户。

Muse 与 Stripe Link 对接，结账使用一次性卡，并在支付前要求人确认；Demo 里绑钱包走显式「Link by Stripe」按钮与条款确认，支付门故意留摩擦，与日历类低风险连接形成对照；Underdog 同样走一次性卡路径，公开商业表述与交易抽成相关，购物研究可在本机完成，扣款仍需批准。dots 与 Grok Bot 将改密、对外共享、影响账户的动作放进自动评审或审批卡；OpenMausBot 公开材料把 shell、文件改动与高风险步统一收成聊天内 Allow / Deny 卡，未单独宣称一次性支付卡路径——「搜得到」与「付得出」仍应按审批对象是否绑定金额与商户来核对。对分析而言，支付场景的价值不在「会不会买」，而在是否把金额、商户、凭证作用域绑在一次明确批准上。

四类场景共用同一组底座：入口与意图、记忆、执行面（任务闭环）、审批与凭证。下一节按五块对照七家材料。

2. 技术架构：五块可对照积木

2.1 入口与调度

Qwen-Live-Harness 把系统拆成 Host 与 daemon：Host（Electron）负责麦、屏、呈现与系统权限；daemon 负责对话、工具、后台 harness、Proactive 与 Memory；二者经本机 WebSocket 通信。理解侧默认走云端 Qwen Omni Realtime；复杂执行可委托本机 ACP 后端（Qwen Code、Codex、Claude Code、Gemini CLI 等）。不装后台 harness 时，仍可做音视频交互、搜索、主动提醒与记忆——采集面不必塞满执行器。

云产品侧则常见 thin client：Muse 客户端经安全通道连到用户 VM；dots 在 ChatGPT、Slack、Teams 收发意图，工作在云电脑上继续；Grok Bot 在桌面与移动端收消息，主执行面在 Cursor 云电脑。OpenMausBot 的公开架构更接近「本机 thin UI + 本机 harness」：React 应用经 HTTP 发命令、经 SSE 收事件；127.0.0.1 上的 harness 持有全部 agent 进程，并把各提供商原生协议归一成一条事件流；Electron 桌面壳内嵌该 harness。共同点是：采集与呈现可以很薄，协调与执行可以侧置；差别在侧置目标是本机 daemon/ACP/harness，还是一人一电脑的云 VM（OpenMausBot 还可把执行面再挂到 Boat 云桌面或 Local VM）。选型时若先定「入口形态」而不定执行面，后面的审批与凭证设计会对不齐。

消费端界面把「主动」写成可操作原语，而不只写在发布文案里。Lightning Demo 中 Muse 客户端可见：Soul（系统指令）与 Memory（长期事实）可检视与改写；Goals 按 Health、Relationships、Finance 等分类提供上下文；Ideas 根据近期对话生成提案，确认后可设为日/周/月 recurring（任务日志里可见添加 cron）；Artifacts 收生成物；通知用于异步 ping。这些控件对应同一执行面——用户的 Secure VM——把「持续跑着的个人 Agent」落成可核对的产品表面。

2.2 记忆：证据层与归属

PersonOS 把记忆写成可检视的链：原始陈述保留为 evidence；情景（episode / cell）保留上下文；atoms 承载可检索事实；chains 连接前后陈述并保留历史；profile 再做画像汇总。框架只向宿主 Agent 提供 materials，生成权留在宿主；无个人内容的片段可以只留证据、不产事实。默认存储可落本地 SQLite，提取与向量则依赖配置的远端模型——「记忆库在本地」与「抽取模型在本地」需要分开写。

2.3 任务闭环光谱

把七家放在一条光谱上，比「本地好 / 云端好」更贴近公开设计：

1本机闭环2云端一人一电脑3只记忆
  1. 本机闭环：Underdog 在用户电脑上跑推理、浏览器与多数办事逻辑；邮件同步仍连提供商。Qwen-Live-Harness 的文件与命令执行落在本机 ACP/CLI；理解多在云 Omni。OpenMausBot 默认也把 agent 进程钉在本机 harness：Bot 跑在已登录的 claude / codex / grok CLI 上，无中间代理；本机路径的上限同样是设备算力、电池与是否开机。
  2. 云端「一人一电脑」：Muse Secure VM、dots 的 cloud computer、Grok Bot 的 Firecracker microVM（用户之间隔离；同一 Cursor 用户下多个 Bot 共享一台电脑）。合盖后任务可继续；浏览器、文件系统、终端是一等公民。Muse 的 Demo 进一步把 persistent 浏览器与 recurring/cron 提案绑在这台 VM 上：主动环不是单次 tool call，而是可挂起的定时任务。dots 还可再挂一台本机作为第二执行面；Grok Bot 可再委派 Cloud Agent 或对注册电脑跑命令——第二面存在时，权限与会话通常仍按「主电脑 / 本机」分别计数。OpenMausBot 落在光谱中间偏本机一侧：默认本机 harness，但可为每个 Bot 挂 Boat 云 Linux 桌面或隔离 Local VM；产品文档另写可选的 always-on Cloud / 自托管服务，用于合盖后继续跑——与「纯本机默认」要分开核对。
  3. 只提供记忆、不提供办事闭环：PersonOS。宿主仍需自建 harness 与审批。

取舍可以直接写成工程参数：本机侧换数据驻留位置与算力上限；云 VM 侧换 always-on 与重活能力，并引入运营方对 VM / 轨迹的访问策略。Muse 另规划用户持有密钥的 Confidential VM；dots 与 Grok Bot 用计划类型与设置项表述训练与数据用途。光谱中间没有「纯本地又永远 online 且无限算力」的点；产品文案若同时承诺三者，需要回到具体外联白名单与模型位置核对。

2.4 审批门

外向动作的门，各家命名不同，结构接近：策略层先判，必要时弹到人；内置安全不被用户规则关掉。

  • Underdog：敏感下一步与支付前要求批准；本机 vault 按账户存密钥。
  • Muse：Sentinel 是连接器动作与网络出口的唯一授权方；Muse 只能提出，Sentinel 批准、拒绝或问人。问人时走客户端系统对话框，不走与 Muse 的聊天线程，降低「对话里伪造同意」的面。发信与购物默认要人确认；批准可按一次、会话、任务、时限或长期授权绑定到具体目的。Lightning Demo 里取消订阅前，Agent 先用编号访谈确认参数（是否必须先问、哪些服务跳过），并在 Tasks 中提供可展开的后端步骤日志（含 API、生图、adding cron 等），把「门开了」与「事办到哪一步」拆开呈现。
  • dots：auto-review 对照说明、Custom Rules 与安全要求，决定放行、先问或交给用户；改密等步骤保留给人。Custom Rules 不能压过内置安全。主动研究（proactive research）使用已连接应用的只读工具集，写操作仍回权限路径。
  • Grok Bot：Auto-review 覆盖 shell、连接器、电脑操作、自动化写入与委派；需要时出审批卡（Allow once / Always allow / Deny）。Ask first 规则优先于放行规则。邮件在例程或非当轮明确请求等触发下可先 draft。
  • Qwen-Live-Harness：后台 harness 的工具权限由后端自身的 ask / allow-all 等策略决定；Host UI 可处理权限请求与任务进度。
  • OpenMausBot：permission broker 把 shell、文件编辑与提问收成聊天内 Allow / Deny（或作答）卡；仓库说明写明对云桌面与本机电脑同样生效，同时注明覆盖面依赖引擎与工具，不保证每一个动作都会暂停。触发器（日程、webhook、连接器 app event）由 Bot 用工具创建/暂停/编辑，人侧可在 Triggers 页检视；导入的 team 包默认连接关闭、例程暂停。

共性还有一条操作语义：批准不等于已经执行成功。预订页失败、支付被拒、连接器超时，都需要产品把「门开了」和「事办成了」分开呈现；Muse、dots、Grok Bot 与 OpenMausBot 的公开说明都强调回顾已完成动作与后果，而不是只展示一次同意。对集成方而言，审批卡的对象应是可识别的目标与效果，而不是模糊的「继续」。

2.5 凭证与外联边界

跨产品重复出现的硬约定是：模型上下文尽量不持有真实密钥。

Muse 用 hatch-authd 发 surrogate，Sentinel 在出口处替换为真凭证；运行时 cell 内的代码与主 Agent 看不到 OAuth 真 token。浏览器登录经客户端进安全存储；浏览器子代理读 accessibility tree，而不是可执行页面脚本随意刮密。dots 用私密登录表单，凭证进云浏览器会话而非对话文本。Grok Bot 用 Vault、Secure Form 或连接器后端 token，填充时模型看不到密码或卡号；连接器 token 留在 Cursor 后端，不落在云电脑磁盘上当明文给模型读。Underdog 强调每账户 vault、密钥留在本机。OpenMausBot 把提供商密钥与集成密钥写在本机配置里，UI 侧只暴露「已配置」类 write-only 标志；应用连接走 Composio OAuth；本机控制需显式 opt-in，且受平台安全门限制。仓库另注明 CLI/openmausbot 路径下 API 密钥以明文保存在私有 config.json（Unix 上 0600）——「密钥不进模型上下文」与「磁盘上如何存放」仍是两句不同的话。

「本地」也不等于零外联。Underdog 的邮件同步、已批准外发与预订仍会出网；Naval mode 是显式断外联开关，而不是默认态。OpenMausBot 本机 harness 默认不出项目方代理，但模型请求仍发往用户所选提供商，Composio / Boat 等可选集成各自出网。云 VM 产品则把外联写成策略对象：Muse 的 runtime cell 与 cell 外的 Sentinel、authd、safety 分类器分域；未读用户数据的干净进程与已 tainted 进程，自动放行范围不同。dots 把渠道、插件、本机连接拆开授权。写产品说明时，把「推理在哪算」和「哪些 socket 被允许」分成两句，可以减少「100% local」类表述与真实流量日志对不上的情况。

4. 一条串景：会后到支付

以「开完会 → 纪要进记忆 → 改日程 → 浏览器订会议室并支付」为例，只标机制落点。

  1. 采集：录音或导入到达入口。Qwen 路径上，Host 采音视频，daemon 协调；云产品路径上，客户端把材料送进 VM 或云电脑工作区；OpenMausBot 路径上，材料进本机 harness 工作区（或 Bot 所选电脑面）。入口此时只解决「材料进得去」，不决定事后能不能静默发信。
  2. 纪要与记忆：转写与决议写入执行面所在存储。若接 PersonOS 一类证据层，原始语句进 evidence，决议进 atoms/chains，供后续检索；Underdog 写本机记忆项；Muse、dots、Grok Bot 写 VM 或 Bot 侧笔记与文件；OpenMausBot 写本机 transcripts / 工作文件夹。此步的外联主要是转写/抽取所用的模型 API（若未本机化），以及是否把轨迹送去训练。
  3. 改日程：读日历冲突、写出新事件。读权限可较宽；写权限在 Muse 连接器策略、dots 插件权限、Grok 连接器与 Auto-review、Underdog 本机批准、OpenMausBot 的 Composio 连接加 permission broker 卡中分别受约束。写入成功与否应回读日历源，而不是以模型口头确认为准。
  4. 订会议室：浏览器跑腿落在默认执行面——云浏览器、本机浏览器，或 OpenMausBot 所选的 Boat 云桌面 / Local VM /（opt-in）本机。页面内容对模型可见，但登录密码按各产品设计走 surrogate、私密表单、vault 或 OAuth 会话。若站点要求验证码或风控，流程在人接管处停下。
  5. 支付：结账页触发支付门。Muse 与 Underdog 的公开路径使用一次性卡并要人确认；其他产品至少把影响资金或账户的步骤送进评审或审批卡（OpenMausBot 公开路径强调高风险动作出 Allow / Deny，未单独描述一次性卡）。批准后仍可能因商户或网络失败而未完成，状态以支付与订单回执为准。

这条链路里，记忆、闭环、审批、凭证是四道不同的闸。同一句用户指令可能穿过多层，但产品若把四道闸收成一个「全自动」开关，出问题后难以定位是记错、跑错机器、门没开，还是凭证作用域过宽。

5. 可观察的对照标准

综合公开机制，评估一款个人 Agent 时，有三条不必依赖口号、可以直接核对的标准：

  1. 记忆是否可检视：用户能否打开材料、出处或记忆项并编辑删除；仅有「更懂你」的描述、无法核对证据时，正确性与隐私声明都缺少审计面。
  2. 外向动作是否有门：发信、日历写权限、下单与支付是否默认经过策略层或人批；批准与执行成功是否分开呈现；用户规则能否压过内置安全（公开设计里通常不能）。若产品提供 Ideas / recurring / cron 一类主动环，还应能核对提案如何变成定时任务、以及任务日志是否可审。
  3. 外联与训练/运营边界是否写清：本机产品的同步与已批外发白名单；云 VM 产品的 egress 策略、运营方访问范围、训练 opt-out 或计划级默认值。本地推理不等于零 socket；一人一电脑也不自动等于「服务商不可读」。

按上述标准回看七家材料：差异已经落在闭环位置、审批门与凭证是否进入模型，而不是落在是否宣称「个人」或是否先做出某一外壳。形态可以后定；这三处机制则已经有足够公开文本可供对照。
