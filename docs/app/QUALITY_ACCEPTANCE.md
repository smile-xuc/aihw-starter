## V01：回答菜品，同时保留不确定性

原问题：**这是什么菜？辣不辣？** 输入保持示例图＋示例语音。下面四项都是必需项；接受自然表达和同义改写，不要求逐字复现参考措辞。

| 检查 ID | 通过标准 | 失败例子 |
|---|---|---|
| V01-01 | 回答与图中的炒菜相符。可以说“看起来像宫保鸡丁”，也可以只描述看起来像鸡块、花生和干辣椒的食物，不强制唯一菜名。 | 识别成图片中没有的汤、披萨等，或完全没有回应菜品问题。 |
| V01-02 | 区分可见干辣椒、常见做法与实际辣度；回答实际辣度无法仅凭图片确定，可以建议询问店员或做菜者。 | 把“肯定不辣”“确定微辣”或具体辣度当作已知事实。 |
| V01-03 | 配方、甜咸、产地和营养数字未出现在输入时，不将它们描述为已验证事实。条件式介绍常见做法可以接受。 | “这盘一定加了某调料”“热量恰好为某数字”，且没有不确定性说明。 |
| V01-04 | 两三句中文能回应两问，结论易懂；不把回答扩展为无关菜谱或大量无法核对的细节。 | 只回答菜名漏掉辣度，或用与图无关的大段内容代替回答。 |

北京地域的播报另按 [VERIFY_BROWSER](VERIFY_BROWSER.md) 记录实际播放结果；合成 URL 就绪不等于已听到音频。内容合格也不代表播报或费用已经通过验收。

**归因口径：** 若逐字稿凭空出现回复、决定或其他说话人，记录“转写错误”；若逐字稿仅有原问句，但纪要添加决定、待办或菜品答案，记录“摘要错误”。如果根本未执行某阶段，标“未核对”，而不是自动通过。内容判定不要求逐字措辞；网页的响应契约仍须满足。若模型返回不被网页接受的格式，记运行未完成，不能仅凭合理的拒绝文字判整条体验通过。

## 如何记录和下结论

复制 [结果记录模板](QUALITY_RESULT_TEMPLATE.md)，每次尝试单独填写。检查结果只使用 `通过`、`失败`、`未核对`；尚未实际执行的用例保持 `未运行`。不要先填一个看似真实的请求 ID、评分或费用。

- 原始证据用网页导出的 `aihw/trace@0.1`；核对 `mode: live`、运行时间、输入路线与实际模型。仅凭导入文件里的 `live` 字段不能证明调用发生，需要对应实际执行记录。
- 回答、转写和纪要从 `outputs[].text` 核对；模型与请求 ID 从 `result.usageRecords` 核对，错误调用也可能放在顶层 `usageRecords`。每条判定摘录对应输出，注明检查 ID；问题没有在轨迹中完整保留时，在记录表里另记固定用例 ID 和问题原文。
- 接口没有成功返回可评分结果，记为“运行未完成”，同时保留已产生的请求和用量；不要把空响应算成模型通过了“不编造”。
- M01/M02 的转写若先丢失事实，标 `ASR` 原因；转写正确但纪要错误，标 `纪要` 原因。二者有一项关键事实失败，该用例就未通过端到端质量验收；不因后续摘要“正确概括了错误转写”而忽略上游问题。
- 单个用例的全部必需项均通过，才能写“该用例通过”。有失败项就失败；没有失败但有未核对项，结论为未完成。不做平均分抵消日期、责任人或无依据断言等关键错误。
- 四例全部通过，只能说明这组固定样本首次验收通过。它不证明复杂照片、噪声录音、长会、不同口音或长期可靠性，也不自动改变商业项目定位。后续用授权的真实素材扩大覆盖。
- 费用用现有账本核对实际请求 ID、用量、价格和同范围账单。质量、实际播报、费用与设备验收分别记录；缺失用量仍为未知，mock 不计实测费用。

## 验收后推进什么

1. 用户回到电脑后，补云环境 Pages 白名单以复查已发布页面；真实模型调用所需的地域接入点、权限、凭证和费用上限另外确认。页面域名放行不等于模型服务已可用。
2. 先完成 V01 与 M01 的两条核心路线，再在同意的费用范围内运行 V02 与 M02。发现问题后保留失败输入和输出，针对具体原因修改并复验。
3. 取得真实效果、用量和账单依据后，优先考虑 Camera → 一看即懂的实机采集链路，复用已完成的上传与结果能力；板卡选择、采购、烧录及实拍仍需实物参与。
4. 商业资料的下一项是选定品类内的项目选型对照，比较交付范围、集成条件和有依据的费用。原生 APP、实时桌宠和更多技术栈继续按原计划后排。
