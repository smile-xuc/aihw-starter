## 〇、先建立直觉：模型在「打草稿」

大模型生成回答时不是一口气写完的，而是一个词一个词往外蹦。生成每个新词时，它都需要回看前面说过的所有内容。为了不用每次都从头重算，推理框架会把前文的中间计算结果缓存下来——这份缓存就是 **KV Cache**（Key-Value 缓存）。

用一个类比：模型权重是「教科书」，大小固定；KV Cache 是「草稿纸」，聊得越久、上下文越长，草稿越厚。

关键事实：**长上下文场景里，先占满显存的是草稿纸，不是教科书。** 一个 7B 级模型按 INT4 存权重只要 3–4 GB，但几万 token 的上下文攒出来的 KV Cache 可以达到同一量级甚至更大——而且每路并发对话各有一份草稿。

## 一、显存账：草稿纸有多厚

KV Cache 的大小可以按量级估算：

```
KV Cache ≈ 2（K 和 V 各一份） × 层数 × KV 头数 × 每头维度
           × 每元素字节数 × 上下文长度 × 并发数
```

几个决定性因子：

| 因子 | 谁决定 | 能不能省 |
|---|---|---|
| 层数 / 头数 / 维度 | 模型结构，选型时定死 | 不能（GQA/MLA 等结构优化除外） |
| 上下文长度 | 场景需求（长文档、长对话） | 砍上下文 = 砍能力，通常不愿意 |
| 并发数 | 业务量 | 砍并发 = 砍吞吐，同样不愿意 |
| **每元素字节数** | 存储精度 | **可以省，这就是量化的切入点** |

前几项都动不了，唯一好动的就是「每个数用多少字节存」。原始精度 FP16 每个数占 16 bit；如果能压到 3–4 bit，同样的显存就能装下 4–5 倍长的上下文，或 4–5 倍的并发。

## 二、量化：把 16 个格子换成 3–4 个

量化（Quantization）的本质是**用更少的 bit 表示同一个数**。16 bit 能表示 6 万多个不同等级，4 bit 只有 16 个等级，2 bit 只剩 4 个——bit 数越少，「刻度」越粗，还原出来的数越不精确。

这和 [02 篇](./02-model-size-chips.md) 讲的权重量化（INT8/INT4）是同一个原理，只是对象不同：

| | 权重量化 | KV Cache 量化 |
|---|---|---|
| 压的是什么 | 教科书（模型参数，静态） | 草稿纸（推理中间结果，动态生成） |
| 什么时候压 | 部署前离线做一次 | 推理过程中在线做，每个新 token 都要压 |
| 主要收益 | 模型放得进小内存设备 | 同样显存下支持更长上下文、更高并发 |
| 难点 | 有充足时间离线校准 | 必须快（在生成链路上），且数据分布事先未知 |

## 三、为什么不能直接粗存：巨值问题

直觉方案是「每个数直接四舍五入到最近的粗刻度」。实际会翻车，原因是**巨值（outlier）**：

一排数里只要混进一个特别大的数，量化范围就必须撑大到能容纳它——刻度被巨值撑粗后，其余大量的小数字全都挤在一两个刻度里，还原出来面目全非。就像用一把最大量程 1000 米的尺子去量一群身高 1.7 米左右的人：尺子刻度是 10 米一格，所有人都被记成「0 到 10 米之间」。

而 Transformer 的 K/V 向量恰恰天然带巨值——某些维度的数值经常比其他维度大一个量级以上。所以「直接粗存」在 2 bit、3 bit 这种低位宽下掉分严重。

## 四、先旋转、再分格：低位宽量化的关键一步

近年低位宽量化方案（KV Cache 侧的代表是 Google Research 的 TurboQuant，权重侧的代表是 SpinQuant 等）的共同思路是：**量化前先给数据做一次「随机旋转」**。

三步拆开看：

1. **旋转摊匀**：把整排数乘一个正交旋转矩阵。旋转不丢失任何信息（可以精确转回来），但会把巨值「摊平」到所有维度上——转完之后数据分布变得均匀、可预测，没有谁特别突出。
2. **按已知分布最优分格**：摊匀后的数据服从一个数学上已知的分布，最优的量化刻度线可以**离线预先算好**（Lloyd-Max 量化），推理时直接查表，不用现场校准。
3. **用的时候转回来**：旋转矩阵选正交矩阵（逆 = 转置），且常用只含 ±1 的 Hadamard 矩阵——逆旋转只需要加减法，计算开销几乎可以忽略。

在此之上还有一类可选的**残差纠错**技巧（如 QJL：把量化误差投影后只存正负号，每维 1 bit），用少量额外存储换回一部分精度——是否值得开，各家工程实测结论并不一致。

> 每一步的数值变化，交互页用「8 门课成绩压缩成 2 bit」的例子做了单步演示：[交互式学习页 · 第 3 层](https://smile-xuc.github.io/aihw-starter/kv-cache-quantization.html#l3)。

## 五、实际部署口径：3–4 bit，收益是「容量换长度」

论文口径和生产口径要分开看：

| 口径 | 位宽 | 精度损失 | 说明 |
|---|---|---|---|
| 论文演示 | 2 bit | 标准评测集上很小 | 教学与极限压缩演示 |
| 论文推荐 | 约 3 bit | 接近无损（标准评测） | 含范数等开销后约 3.1 bit/元素 |
| 生产主流 | **4 bit** | 长上下文与高难推理任务上更稳 | 主流推理框架（如 vLLM）与芯片厂商评测后的保守选择，KV 容量约提升至 3–4 倍 |

两点工程共识：**bit 数不是越低越好**——3 bit 在标准评测上近无损，但在长上下文、多步推理这类难任务上会露怯，所以生产环境普遍停在 4 bit；**收益按「同显存装多长上下文」来算**——KV Cache 压到 1/4，意味着同一张卡支持的上下文长度或并发路数翻到约 4 倍，且显存打满时长文生成反而更快（要搬运的数据变少了）。

## 六、对做硬件意味着什么

[02 篇](./02-model-size-chips.md)的结论是端侧推理「瓶颈在内存容量和带宽」。KV Cache 量化在两头都有直接影响：

1. **长上下文在小内存设备上的可行性**：端侧设备内存本就紧张，权重量化解决「模型放得下」，KV Cache 量化解决「聊得久、读得长」。两者叠加，才能在 8–16 GB 级设备上支持几万 token 的上下文——录音卡的整场会议纪要、IPC 的长时段视频摘要，都吃这个红利。
2. **云端成本直接联动**：云推理按卡算钱，KV 容量提升 3–4 倍 ≈ 同一张卡多服务 3–4 倍并发。做「硬件 + 云订阅」生意时，这类推理侧优化会逐步反映在 API 价格与订阅毛利上——算账口径见各品类的 `03-cost.md`。
3. **选型时可以问方案商的一个问题**：「KV Cache 用什么精度存？」——如果答案是 FP16 且场景涉及长上下文，显存与成本估算大概率偏乐观。

## 七、给 AI 硬件从业者的检查清单

评估长上下文场景（会议纪要、长文档、长陪伴对话）的推理成本前，过一遍：

1. **算 KV Cache 账，不只算权重账**：按第一节公式估算目标上下文长度下的草稿纸大小，和权重占用放在一起看
2. **确认推理框架的 KV 量化开关**：主流框架已内置 4 bit KV Cache 选项，属于「改一个启动参数」级别的优化
3. **难任务单独回测**：4 bit 在闲聊场景几乎无感，但多步推理、代码、长文引用类任务要单独跑一轮评测再上线
4. **端侧方案问清楚 KV 精度**：同一颗芯片，KV Cache 存 FP16 和存 INT4，可支持的上下文长度差 4 倍
