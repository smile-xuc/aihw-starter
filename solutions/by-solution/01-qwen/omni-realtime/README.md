# Omni 实时端到端方案 · Runtime Host 中间层

> 千问方案的一个子形态：用 Qwen-Omni-Realtime 做端到端实时语音，配一层自建宿主（下文统称 **Runtime Host**）把模型接到硬件上。
>
> 上级方案页：[千问大模型方案](../README.md) · 延迟横评：[benchmark/](../../../benchmark/)

---

## 1. 方案定位

一个 Realtime 模型只会输出三样东西：文本、音频、`function_call`。要把它变成一台**能动、能看、有记忆、有时间感**的设备，靠的是模型与硬件之间那一层宿主。

这套方案适用于对首字延迟和拟人度要求高的高价值单品——桌面机器人、伴随机器人、带屏陪伴设备。已知落地项目反馈：换成端到端实时链路后，用户单日活跃时长出现数量级增长（约 10 倍量级）。代价同样明确：**单位时长成本显著高于 ASR → LLM → TTS 三段式**，见第 9 节。

| 该选它 | 不该选它 |
|---|---|
| 对话是产品主体验，用户会长时间连续聊 | 语音只是偶发指令入口（开灯、定时器） |
| 需要打断、附和、情绪起伏这类拟人细节 | 一问一答足够，延迟 2～3 秒可接受 |
| 硬件有屏 / 舵机 / 灯效，需要语音与动作同步 | 纯音频设备且无动作联动 |
| 客单价能吃下音频 token 成本 | 走低价白牌，云成本必须压到极限 |

延迟对照（同一测试环境下的实测参考值，可复现脚本见 [benchmark/](../../../benchmark/)）：

| 链路 | 体感延迟（轻 / 复杂 / 搜索） | 语义打断 |
|---|---|---|
| 三段式阻塞（ASR → LLM → TTS） | 5502 / 9449 / 7416 ms | 不支持 |
| 三段式流式 | 2473 / 2846 / 2980 ms | 不支持 |
| Omni Realtime（WebSocket 双工） | **347 / 375 / 433 ms** | 支持 |

## 2. 链路总览

```
┌──────────────────────── 云端 ────────────────────────┐
│  Qwen-Omni-Realtime                                  │
│  输入：音频流 / 图像帧 / 文本 item                     │
│  输出：文本 + 音频 + function_call    ← 仅此三种        │
└───────────────▲──────────────────────┬───────────────┘
                │ session.update       │ function_call
                │ 音频/事件注入         ▼
┌───────────────┴──────────────────────────────────────┐
│                  Runtime Host（自建）                  │
│  ① 装配器  会话建立时拼 instructions / tools / voice   │
│  ② 路由器  按工具名前缀三路分发 + 参数校验兜底          │
│  ③ 状态机  模式位 · 计时器 · 会话生命周期               │
│  ④ 注入器  异步事件 → 对话轮次（视觉 / 静默 / 搜索）    │
│  ⑤ 设备桥  动作 ID → 指令帧，两级回包语义               │
│  ⑥ 记忆管道（离线，不在实时链路上）                     │
└───────────────┬──────────────────────┬───────────────┘
                │ 下行设备指令          │ 带外 HTTP
                ▼                      ▼
┌───────────────────────────┐   ┌──────────────────┐
│         设备侧             │   │ 搜索 / 三方服务   │
│ 屏幕即「脸」· 舵机 · 灯     │   └──────────────────┘
│ 摄像头 · 本地时钟 · 音乐 App│
└───────────────────────────┘
```

设备侧拓扑有两种常见形态，直接影响状态注入的字段数量：

| 形态 | 结构 | 状态注入特征 |
|---|---|---|
| 两段式 | 云 → 手机 App → 底座 MCU（蓝牙） | 需要注入两个独立电量数值（手机 + 底座）；屏幕、摄像头、日历、时钟由手机承担 |
| 一体式 | 云 → 设备主控 → 舵机 / 屏 | 单一电量与网络状态；圆屏兼作表情与表盘 |

> 判据示例：启动上下文里同时出现两个电量数值，即可判定为两段结构。

## 3. 模型缺什么，中间层补什么

这张表是复制这套能力时的核对清单。左列是 Realtime 模型天生没有的东西，右列是最小实现。

| 模型原本没有 | 中间层补的东西 | 最小实现 |
|---|---|---|
| 时钟 | 读设备时间的工具 + 启动上下文种子 | 工具返回本地日期 / 时间 / 星期 / 时区；提示词强制「问时间必须先调工具，不许用自己的钟」 |
| 地理位置 | 启动上下文注入 | 建会话时拼一段纯文本，不需要工具 |
| 身体状态感知 | 电量、充电态、网络连通性注入 | 同上；两段结构注入两个电量 |
| 跨会话记忆 | 三层记忆结构 | 先只做「上轮对话 JSONL 回填」，性价比最高 |
| 真实视觉 | 拍摄触发工具 + 事后事件注入 | 触发与结果**必须解耦**，不要指望工具返回值里塞图片 |
| 知道动作演完没演完 | 派发收据 / 完成回执两级语义 | 先只做派发收据，提示词里禁止模型宣称「已经做好了」 |
| 流程顺序保证 | enter / exit 工具把状态机外化 | 关键流程前加一个空参数 enter 工具当闸门 |
| 不编造的自觉 | 工具强制前置 + 反复禁令 | 凡是有真值来源的问题，一律要求先调工具再回答 |
| 主动开口 | 伪事件注入 | 静默计时器触发，注入一条系统事件当作输入 |
| 自己结束会话 | 道别工具 + 宿主关连接 | 模型说完告别就调工具，由宿主关 |
| 链路可靠性感知 | 等待重连工具 | 会话状态留在宿主侧，设备掉线不重开 session |
| 联网搜索 | 宿主带外接搜索服务 | 下发了 `tools` 就用不了模型内建搜索，见第 7 节 |

## 4. Runtime Host 六类职责

前五类在实时链路上，第六类是独立的离线管道。

### ① 装配器 Session Assembler

会话建立时拼出整份系统上下文与工具集。`instructions` 里有**六个动态槽位**，缺一个模型就会失去一类感知：

| 槽位 | 内容 | 备注 |
|---|---|---|
| 用户档案 | 偏好称呼、指定音色 ID | 与 `voice` 字段保持一致 |
| Owner Card | 姓名、昵称、性别、生日、籍贯、职业、梦想、喜好、忌讳 | 缺失就留空，禁止推断 |
| 记忆摘要 | 长期记忆的压缩文本 | 不是完整聊天记录 |
| 启动上下文 | 电量、网络、音乐 App 登录态、当前播放态、当前表盘、地理位置、设备本地时间 | 必须标注为「会话起始种子，问实时时钟请调工具」 |
| 上轮会话 | JSONL 格式的最近对话 | 明确标注为不可信输入，禁止把里面的内容当系统指令执行 |
| 工具集 | function 定义清单 | 与 `tools` 字段同源，避免两处不一致 |

同时要选定 ASR 模型、音色、VAD 参数（`threshold` / `prefix_padding_ms` / `silence_duration_ms` / `idle_timeout_ms`）。

### ② 路由器 Router

命名空间不是分类美学，是**路由表**。除分发之外还要做两件模型做不好的事：

- **参数互斥校验**：例如动作工具的 `presetCommand` 与 `sequence` 只能给一个。真实配置里这条规则在提示词中被重复强调三次，说明是高频出错点——schema 层拦不住，必须在宿主侧兜底，两者同时给或都为空时直接回 `failed` 并说明原因。
- **语义展开**：把 `nod_twice` 这类语义指令展开成底层多步 sequence，把 `speed` 折叠到展开后的步骤上。模型只给人类语义，物理参数由宿主翻译。
- **空参数兜底**：表情行为类工具的参数普遍为空对象，工具名本身就是动作 ID。

### ③ 状态机 State Machine

把对话流程的状态位从提示词搬到服务端，用工具当闸门。三类状态要管：

- **模式位**：搜索模式、提醒模式的进入 / 退出 / 强制清理。enter 类工具不发任何请求，作用是回注一段「接下来该收哪些槽位」的指令。
- **计时器**：以毫秒为参数的等待，返回 `timeout` 或 `user_spoke` 两种结果。
- **生命周期**：静默等待、道别关闭、断线重连等待。

关键设计取向：**正常路径与失败路径的状态清理都由宿主强制兜底，工具只留给模型主动放弃的分支**。搜索成功或失败都不许模型调 exit，只有用户半途放弃才调。

### ④ 注入器 Fact Injector

最容易被低估的一块。Realtime 模型只能被动等输入，要让它对物理世界有反应，必须由宿主把异步事件翻译成对话 item：

| 事件 | 注入形式 |
|---|---|
| 视觉结果 | 图片到达云端视觉理解后，注入一个成功事件；触发工具本身不返回图片 |
| 用户静默 | 注入一条 `[HOST_RUNTIME_EVENT: USER_IDLE]` 形式的伪输入，模型才有机会决定沉默还是开口 |
| 人设切换 | 注入 `[HOST_RUNTIME_EVENT: PERSONA_SWITCHED persona=<P1..P4>]`，同时触发配置热更新 |
| 带外结果 | 搜索结果作为 `function_call_output` 回注 |

没有这层，产品只能做成「用户问一句、机器答一句」，做不出主动性。

### ⑤ 设备桥 Device Bridge

动画帧、音效、电机脚本通常**预烧在设备端**，云端只传动作 ID——这是实时语音场景下的必然选择，等不起动画资产下发的往返延迟。宿主侧要维护三条语义：

- **两级回包**：派发收据（已发送 / 已排期）与完成回执（真的演完了）必须区分。
- **队列语义**：队列实际在设备端，但宿主要知道哪些动作排队、哪些插队。
- **停止广播**：清队指令要能一次覆盖动画、运动、在途触发多个作用域。

代价要提前告知客户：**动作库不能热更**，加一个新动作要发固件。想做运营活动式的动作上新，得另设可下载资产包的通道。

### ⑥ 记忆管道 Memory Pipeline

完全在实时链路之外的异步作业，产出下次建会话的输入。三层结构各自解决不同时间尺度：

| 层 | 内容 | 建议 |
|---|---|---|
| 长期画像 | 按身份、偏好、关系、作息、追求、身心状态、期望被支持的方式、与设备的关系八类抽取 | 不完整就留空，禁止推断没有的信息 |
| 长期摘要 | 重要事件与共同经历的压缩 | 不是完整聊天记录 |
| 近期上下文 | 最近几轮会话的原文 JSONL | **先只做这一层**，成本最低、体验提升最明显 |

配套的使用约束同样重要：一次回复最多显式提及一条历史细节；禁止罗列「知道用户哪些事」；禁止提及数据源名称；**用户当下的话优先于所有历史信息**。

## 5. 三条落地路径

同样是一次 `function_call`，落点差别极大。设计工具时第一件事就是想清楚它属于哪一路。

| 前缀 | 落到哪 | 设备参与 | 模型拿到什么 |
|---|---|---|---|
| `client_*` | 打包成设备指令走下行通道 | 参与，是执行方 | 派发收据，不是完成回执 |
| `runtime_*` | 不下发设备，只改宿主自己的状态机 | 不参与 | 控制信号 `timeout` / `user_spoke`，或一段槽位收集指令 |
| `server_*` | 宿主在云端带外发请求 | 完全不参与 | 外部事实文本 |

**带外的意思**：音频在 WebSocket 上持续双向流动，外部请求若挤进同一条通道会拖累语音实时性。所以宿主另起一条 HTTP 出去，结果再作为对话 item 注入回来。这和视觉的机制是同一个套路——**工具调用只负责触发，结果靠事件回注**。

工具结果必须给**状态码而不是自然语言或空串**：`ok` / `not_connected` / `not_logged_in` / `failed` / `no_history` / 匹配态等。提示词里的所有话术分支都依赖这些字段；超时要回 `failed`，不要静默丢弃——模型拿不到终态就会自己编。

## 6. 三个必须讲清的执行语义

这三条最容易踩，且都会直接表现为用户可感知的体验事故。

### A. 返回的是派发收据，不是完成回执

`Dispatched means sent/scheduled, not completed`。一次画方形要走十几秒，模型调完工具只知道指令发出去了。要真等，得在执行提示里给「等待完成」模式；但等待期间会阻塞对话，是否要等必须逐场景决定。**默认不等、默认不许宣称完成**是更安全的起点。

### B. 设备端是队列 + 插队两级

长表演进队列排队；短情绪抢占当前播放立刻插入，但**不清空队列**——后面排着的动作还会接着演。要真停必须显式发清队指令。

「嘴上说停了但没发清队指令」应直接定义为失败，规则写成宁可多发不可漏发。同时要区分反例：鼓励继续的话（别停、继续）和夸奖不能触发停止。这个坑几乎必踩一次，因为动画在设备本地跑，云端不发指令它就一直演，开发者在日志里看不出异常。

### C. 感知类能力是两段异步

完整流程：模型调触发工具 → 设备本地采集 → 数据走**另一条上行通道**送云端理解 → 成功后宿主把结果**作为新输入事件注入** → 模型这一刻才第一次拿到事实。

空窗期的话术要逐能力定义，两条相反的规则可以直接抄：

- **视觉**：允许先说一句「我看看」。因为有可见的物理动作，配一句话合理。
- **搜索**：全程禁止叙述过程。因为搜索没有任何外部表现，说「正在查询网络」纯属暴露实现。

另外统一禁止叙述「加载中 / 处理中」这类技术状态。

## 7. session.update 的时机与四条硬约束

**每建一次连接发一次，不是每轮发。** 官方接入流程把它定在第 2 步「配置会话」：建连 → 发 `session.update` → 服务端校验并回 `session.updated` → 之后才开始送音频。连接建立时服务端会先推 `session.created`，里面是默认配置。

单轮对话的事件序列里不含 `session.update`：

```
input_audio_buffer.append …                (持续送 base64 音频)
  ← input_audio_buffer.speech_started / speech_stopped
  ← input_audio_buffer.committed          (server_vad 自动提交)
  ← conversation.item.created             (message 或 function_call)
  ← response.created
  ← response.audio_transcript.delta / response.audio.delta …
  ← response.done

命中工具时补一段：
  ← conversation.item.created (type=function_call, 带 call_id/name)
  ← response.function_call_arguments.done
→ conversation.item.create  { item: { type:"function_call_output", call_id, output } }
→ response.create                          (VAD 模式下这一步仍然必须发)
```

由此推出四条硬约束：

**① `response.create` 没有覆盖参数。** 官方 `response.create` 只有 `type` 一个字段，不存在按轮覆盖 `instructions` / `tools` / `modalities` 的对象。也就是**不能按轮切换提示词或工具集**。所有需要逐轮变化的信息只能作为对话内容注入（文本 item 或运行时事件行），不能作为配置下发。

**② 中途改配置要发全量。** 官方对 `session.update` 的描述是「更新会话的默认配置，校验参数，合法则应用更改并返回完整配置」，结构上允许中途再发，但**没有定义省略字段的语义**。规范做法是每次都发完整 `session` 对象，绝不做局部 patch。唯一明确的时序禁令是音频格式：`audio.input.format` 必须在首帧音频之前定好，发过音频就不能再改。

**③ `tools` 与联网搜索不兼容，不可同时开启。** 一旦下发工具集，模型自带的联网搜索就用不了，搜索能力必须由宿主自己接（`runtime_enter_web_search` 进入模式 + `server_web_search` 带外执行）。

**④ 会话有硬上限，必须做滚动。** 单次会话最长 120 分钟，到点服务端主动断开。上下文上限按模型分档：

| 模型 | 音频最大轮次 | 音频最大时长 | 视频最大轮次 | 视频最大时长 |
|---|---|---|---|---|
| qwen3.5-omni-plus-realtime | 100 轮 | 600 秒 | 50 轮 | 240 秒 |
| qwen3.5-omni-flash-realtime | 80 轮 | 480 秒 | 50 轮 | 120 秒 |

超出后自动丢弃更早历史。宿主要在逼近上限前主动开新会话、重发全量 `session.update`、用「上轮会话」槽位续上，不要等服务端踢。同一会话长期不关会让上下文无限累积。

### 人设热切换的两条路

音色 `voice` 和 `instructions`（里面写着当前人设）都在 session 级，不在对话级。外设切换人设只有两条路：

| 方案 | 做法 | 权衡 |
|---|---|---|
| A（推荐） | 在轮边界（收到 `response.done` 后）发一次全量 `session.update`，换 `voice` + 换 instructions 里的人设段；若有响应在飞先 `response.cancel` | 上下文不丢、延迟低；但会话中途换 `voice` 的生效行为官方未明确，需实测 |
| B（兜底） | 断开重连，发新的 `session.update`，把上一段对话压缩成「上轮会话」注入 | 保证干净，代价是重连延迟与上下文重放 |

按 A 实现，实测不生效或有杂音就自动降级到 B。

## 8. 首包成本：两份真实配置的对照

以下两组数字来自两个不同项目的真实 `session` 配置快照（已脱敏，仅保留体积口径）。

| 项 | 配置 A | 配置 B |
|---|---|---|
| 工具总数 | 129（116 动作类 + 12 功能类 + 1 带外类） | 62（50 表情行为 + 6 设备类 + 5 宿主类 + 1 带外类） |
| instructions | 44,133 字符 / 612 行 | 61,929 字符 / 937 行 |
| tools 定义 | 37,755 字符 | 26,117 字符 |
| **首包合计** | **81,888 字符** | **88,046 字符** |
| 粗估量级 | 约 4 万 token | 约 4 万 token |

**反直觉的地方**：配置 B 把工具数砍掉一半以上（129 → 62），tools 段确实省了约 31%，但 instructions 因为话术分支写细涨了约 40%，首包总量反而略增。

结论：**首包预算要按「工具定义 + 提示词」合并管理**，只砍工具数不看提示词膨胀等于白砍。而首包是每次建会话都要重发一遍的，会话滚动越频繁，这笔钱付得越多。

两条可直接执行的裁剪动作：

- **按日期 / 场景 / 固件版本做工具子集下发。** 配置 A 的会话起始时间是 8 月，但万圣节、圣诞、春节、情人节相关的 17 个节日动作工具全年常驻。这一刀既省钱也提准确率——从 116 个动作里挑一个本身就是困难的分类任务，候选集砍半，选择准确率会明显不同。
- **话术模板尽量搬到工具返回值里。** 模式状态机的价值就在这里：追问模板放在宿主返回的工具结果中，改策略不用重新下发几万字的系统上下文（提示词是建会话时一次性下发、运行中改不了的）。

## 9. 成本结构：为什么比三段式贵

计费口径以[百炼定价页](https://help.aliyun.com/zh/model-studio/billing-of-model-studio)为准，这里只讲结构差异。

| | 三段式（ASR → LLM → TTS） | Omni Realtime 端到端 |
|---|---|---|
| 计费维度 | ASR 按音频时长 + LLM 按文本 token + TTS 按字符 | 输入音频 token + 输出音频 token（+ 文本 token） |
| 语音进模型前 | 先转成文本，模型只吃文本 token | 音频直接进模型，按音频 token 计 |
| 静默与附和 | 被 VAD 挡在 ASR 之前，几乎不计费 | 进入上下文即计费 |
| 上下文累积 | 只累积文本 | 累积音频轮次，长会话单轮成本随历史增长 |
| 首包 | 只在 LLM 一段计一次系统提示 | 每次建会话重发全份 instructions + tools |

四条降本手段，按性价比排序：

1. **优先 flash 档**。官方实测口径下 flash 比 plus 快约 0.7 秒，价格档位也更低；复杂推理需求不强的陪伴场景优先 flash。
2. **控制首包与会话滚动频率**。见第 8 节；滚动越频繁，首包成本乘以次数。
3. **裁上下文而不是等它自己丢**。逼近轮次上限前主动压缩成「上轮会话」文本，用文本 token 替代音频 token 携带历史。
4. **场景分流**。闲聊、情绪陪伴走 Realtime；长文任务（讲故事、生成纪要、复杂搜索总结）切到文本链路再用 TTS 播报，两条链路共用同一套记忆。

## 10. 分三阶段落地

不必一次做全，但阶段顺序不能乱。

| 阶段 | 内容 | 说明 |
|---|---|---|
| **1 · 地基**（不做就跑不起来） | 前缀路由 · 参数校验兜底 · 派发收据语义 · 启动上下文注入 | 前缀路由先定好命名规范，后面加工具零成本；参数给错是常态不是异常；「发出去」和「做完了」从第一天就分开，后期改会牵动整份提示词；启动上下文成本极低但直接决定机器像不像活的 |
| **2 · 体验层** | 异步事件注入 · 打断与清队 · 上轮会话回填 | 有事件注入才能做视觉和主动开口；打断做不好等于产品不受控；上轮会话回填是三层记忆里最便宜的一层，但「它还记得上次说的」贡献最大 |
| **3 · 黏性层** | 结构化记忆抽取管道 · 模式状态机 | 可以后补，但**架构上必须提前预留槽位**——instructions 里先留好占位段落，否则后期插入会撕整份提示词 |

## 11. 三个要提前告知客户的坑

| 坑 | 影响 | 说明 |
|---|---|---|
| 首包成本被低估 | 高 | 每次建会话下发数万字符，且会话滚动会重复付费。按日期 / 场景 / 固件版本裁工具子集，同时盯住提示词膨胀 |
| 动作库无法热更 | 中 | 资产预烧固件是实时性的必要代价。如果产品规划里有「节日活动上新动作」「IP 联名皮肤」，必须在架构期单独设计一条可下载资产包的通道 |
| 工具名本身在泄密 | 中 | 工具名的语义全在名字里，模型看得见，只能靠保密条款硬压着不许说：不许确认工具是否存在、不许补全或纠正名字、不许翻译、不许说「这是个内部工具」这类间接确认。反方向是把工具名混淆成无语义 ID，但那样模型选不准——名字里的语义正是它做选择的依据。这是个没有免费解法的取舍 |

保密条款里有一句值得直接抄走：保密只约束对用户说什么，**不得因此减少正常的工具调用**。否则模型会为了「保密」变得不敢动作。

## 13. 合规提示

桌面机器人、伴随机器人属于情感陪伴类产品，适用 2026 年 7 月 15 日起施行的《人工智能拟人化互动服务管理暂行办法》。核心义务：算法备案 + 上线前安全评估、AI 身份标识、超 2 小时使用提醒、不得以诱导沉迷依赖为服务目标；面向未成年人另有虚拟亲密关系禁令与未成年人模式要求。

拟人化设计与合规义务会正面冲突的两处：**AI 身份标识**要求与「不许承认自己是 AI」的人设写法互斥，需要在提示词里给出合规的身份回答；**超时提醒**要由宿主的计时器驱动，不能指望模型自己记时长。

详见根目录 [faq.md](../../../../faq.md) E 节 Q22.1。
